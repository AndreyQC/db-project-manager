## Кластер CH и поведение DDL

CH на 10.41.254.51:31023 — это **3-шардовый кластер** (`cluster=default`,
shards 1/2/3, replicas 1), сервер `bi-clickhouse-1-0-0` мы попадаем на
шард 2.

**Проверено `default`-суперюзером** (connection
`10_41_254_51_CH__DB__default__U_default.yaml`):
```sql
SHOW GRANTS FOR default → GRANT ALL ON *.* TO default WITH GRANT OPTION
```

**Рассинхрон кластера — частично исправлен 2026-10-17.** База `cis_etl`
теперь на 3/3 реплик (`CREATE DATABASE cis_etl ON CLUSTER default` выполнен
через `default`-юзера):
```
bi-clickhouse-1-0-0  ✓  (наш текущий)
bi-clickhouse-0-0-0  ✓
bi-clickhouse-2-0-0  ✓  ← восстановлено
```

Таблицы внутри `cis_etl` остались на 2/3 реплик (создавались без
`ON CLUSTER`). Не критично — retry-логика в адаптере это покроет.
Принцип: **DDL в адаптере всегда через `ON CLUSTER default`**, чтобы
новые таблицы были на всех репликах сразу.

Из-за остаточного рассинхрона таблиц:
- `SELECT FROM system.tables WHERE database='cis_etl'` — попадает на
  реплику с таблицами → 10 объектов; либо на пустую → 0.
- `clickhouse-connect` с `database='cis_etl'` в init — падает на инициализации
  (запрос `system.settings` уходит на реплику без таблиц; либо на ту, где
  нет базы — тогда `Code: 81`).
- `DROP TABLE cis_etl.test_table` через HTTP — retry 5 раз сработал.

**Конфигурация адаптера (итог):**

1. **Юзер:** `default` (полные права). Пароль из
   `connections/10_41_254_51_CH__DB__default__U_default.yaml`, расшифровка
   через `Fernet(ENVOS_CRYPTO_01)`.

2. **`clickhouse_connect.get_client(...)`:** НЕ передавать `database=` в
   init (иначе падает на пустой реплике). Использовать полные имена
   `cis_etl.table_name`.

3. **`command()` с retry:** при `Code: 81 UNKNOWN_DATABASE` повторять
   3-5 раз с паузой 1-2 сек.

4. **DDL-операции:** всегда с `ON CLUSTER default` для синхронного
   создания/дропа на всех репликах. Пример:
   ```sql
   CREATE TABLE cis_etl.foo (...) ENGINE = MergeTree ORDER BY tuple()
   ON CLUSTER default
   ```

5. **`hrdo_user`:** НЕ использовать для DDL (только SELECT к `cis_zup` и
   `cis_etl`).

## Пример подключения

```python
import clickhouse_connect, time
from cryptography.fernet import Fernet
import os, yaml

cfg = yaml.safe_load(open('connections/10_41_254_51_CH__DB__default__U_default.yaml'))
pwd = Fernet(os.environ['ENVOS_CRYPTO_01'].encode()).decrypt(
    cfg['password'].replace('crypto__ENVOS_CRYPTO_01__', '').encode()
).decode()

c = clickhouse_connect.get_client(
    host=cfg['host'], port=cfg['port'],
    username=cfg['username'], password=pwd,
    send_receive_timeout=30,
    # НЕ передавать database= — иначе init падает на пустой реплике
)

def ch_command_with_retry(c, sql, retries=5):
    for i in range(retries):
        try:
            c.command(sql)
            return True
        except Exception as e:
            if 'UNKNOWN_DATABASE' in str(e) and i < retries - 1:
                time.sleep(1.5)
                continue
            raise
```

## Фаза 3 (2026-10-17) — Phase 10: deploy journal

В PG deploy journal живёт в каждой target-БД как schema `__deploy`. В CH
нет схем — поэтому журнал живёт в **отдельной БД `__deploy`**, общей для
всех целевых БД. Каждая строка несёт дискриминатор `target_db`.

### DDL `__deploy` (3 таблицы, на 3/3 реплик)

```sql
-- schema_version (MergeTree, append-only)
CREATE TABLE __deploy.schema_version ON CLUSTER default
(
    id           UInt64 DEFAULT 0,
    target_db    String,
    version      String,
    applied_at   DateTime64(9, 'UTC') DEFAULT now64(9),
    source       String
)
ENGINE = MergeTree ORDER BY tuple() SETTINGS allow_nullable_key = 1

-- script_history (ReplacingMergeTree, UPSERT по executed_at)
CREATE TABLE __deploy.script_history ON CLUSTER default
(
    target_db      String,
    script_name    String,
    script_type    String,
    checksum       String,
    success        UInt8,
    executed_at    DateTime64(9, 'UTC') DEFAULT now64(9),
    error_message  String,
    duration_ms    Int32
)
ENGINE = ReplacingMergeTree(executed_at) ORDER BY (target_db, script_name, script_type)

-- script_audit_log (MergeTree, append-only)
CREATE TABLE __deploy.script_audit_log ON CLUSTER default
(
    id              UInt64 DEFAULT 0,
    target_db       String,
    script_name     String,
    script_type     String,
    checksum        String,
    success         UInt8,
    error_message   String,
    duration_ms     Int32,
    executed_at     DateTime64(9, 'UTC') DEFAULT now64(9),
    deploy_version  String,
    deploy_source   String
)
ENGINE = MergeTree ORDER BY tuple() SETTINGS allow_nullable_key = 1
```

### Реализованные методы адаптера (Phase 10)

| Метод | Реализация |
|---|---|
| `get_schema_version(target_db)` | `clusterAllReplicas` + `row_number() OVER (PARTITION BY target_db ORDER BY applied_at DESC)` |
| `record_schema_version(target_db, version, source)` | INSERT (через `_cmd_with_retry_params` с `%(name)s` биндингом) |
| `get_script_history(target, name, type)` | `clusterAllReplicas FINAL` — финальный ReplacingMergeTree |
| `record_script_execution(target, record, ...)` | UPSERT (ReplacingMergeTree) + audit insert, два шага |

### Helpers

- `_cmd_with_retry_params(sql, params)` — то же что `_cmd_with_retry`, но
  с `client.command(sql, parameters={...})` (injection-safe).

### Cluster desync: чтение через `clusterAllReplicas`

Без `clusterAllReplicas` запись могла попасть на реплику A, а чтение
выполниться с реплики B (тогда результат пуст). Фикс — все SELECT
по `__deploy.*` используют `clusterAllReplicas('default', __deploy.X)`.

## Phase 5.6 (2026-10-17) — Per-target deploy journal (commit `c52db57`)

**Изменение дизайна:** shared `__deploy` БД → per-target таблицы в каждой user-БД.
Причина: пользователь хотел "одна БД = самодостаточный каталог" — текущая
shared-`__deploy` БД нарушала этот принцип (deploy journal был общим для
всех целевых БД). В PG журнал живёт в `__deploy`-схеме каждой target-БД;
в CH (где нет схем) журнал теперь живёт в самой target-БД с префиксом
`deploy_` в именах таблиц.

| `__deploy.script_history` с `target_db` колонкой | `<target>.deploy_script_history` |
| `__deploy.script_audit_log` с `target_db` колонкой | `<target>.deploy_script_audit_log` |
