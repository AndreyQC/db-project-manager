## Что это за проект

Python-инструмент (PostgreSQL/Greenplum) для reverse-engineering БД в дерево SQL-файлов,
построения графа зависимостей, validation deploy на пустую temp-БД, сравнения состояний
и controlled-deployment. Стек: Python 3.13, uv, pydantic v2, typer (CLI), PySide6 (GUI),
sqlglot, testcontainers. Пакеты: `domain` → `infrastructure` → `application` →
`presentation`.

## Delta относительно 20260814_002

Закрыт BACKLOG P1 «database_setting empty query» — последние 2 падающих
integration-теста. Итог: **integration-прогон полностью зелёный (16 passed)** —
блокер для Phase 12 убран. Кодовой части фаз не менялось; изменения —
deploy-фикс + ремонт integration-инфраструктуры.

Вскрылись **три** независимые причины (гипотеза бэклога подтвердилась лишь частично):

1. **Comment-only скрипт** (гипотеза). `_get_database_properties` всегда непуст
   (encoding/lc_collate/lc_ctype) → `settings/database settings.sql` эмитится даже
   при пустых settings → body = только комментарии → psycopg2
   `can't execute an empty query`. Вариант «RE не эмитит файл» отвергнут:
   autodoc-заголовок несёт `db_properties` для `CREATE DATABASE` temp-БД.
   Фикс: `_deploy_object` пропускает comment-only скрипты (вершина остаётся
   в графе).
2. **Баги сетапа `test_phase5_extensions_e2e`:** `CREATE EXTENSION uuid-ossp`
   без кавычек (имя с дефисом = SyntaxError); латентные: устаревший
   `build_only=True` (API-дрейф) и фильтр ключей `"function public.f"` под
   старый формат object_key.
3. **Межтестовая контаминация:** общая БД `postgres` контейнера накапливала
   объекты от предыдущих тестов → order-dependent падение qualify-теста на
   `_validate_deploy_presence`. Фикс: пер-тестовые БД в `pg_conn_cfg`.

## Key decisions & constraints (новое)

- Comment-only скрипт — **не ошибка деплоя, а валидный случай**: файл может нести
  метаданные (autodoc) без исполняемого SQL. Пропускать, а не блокировать.
- Определение «пустого» SQL обязано учитывать кавычки: `SELECT '--'` — исполняемый
  SQL. False-«пусто» = тихая потеря оператора (хуже исходного бага).
- Integration-тесты на общем состоянии БД — order-dependent по построению;
  пер-тестовая БД дешевле, чем детерминированный teardown каждого теста.
