## Delta относительно 20260902_002

**Phase 15.5.2 (cis_zup feedback 2026-09-02 повторный прогон).**

После фикса `DIFFED_TYPES + schema` (15.5, commit `606cd3d`) deploy apply
перестал падать с `InvalidSchemaName` для пользовательских таблиц, но
**не создавал `__deploy` schema +3 таблицы** на пустой target-БД.
Root cause — `ReverseEngineerService._seed_or_sync_deploy` всегда
seed'ит canonical `__deploy` файлы в temp_root, в том числе когда
RE вызывается через `CompareService._build_db_side` для snapshot'а
target-БД. Compare видит их → comparator UNCHANGED → DeltaPlan
`action=skip script_file=''` для `__deploy` → apply ничего не делает.

**Решение (компромиссное, не чистое):** отдельная утилита
`db-pm deploy init-service-schema --target-connection-file ...`,
которая проверяет **реальное** состояние target-БД через
`adapter.get_database_structure()` (не через snapshot!) и идемпотентно
создаёт `__deploy` schema + 3 таблицы через
`CREATE SCHEMA IF NOT EXISTS` + `CREATE TABLE IF NOT EXISTS` из того же
`canonical_deploy_ddl()` шаблона, что RE / yaml apply.

Полное (правильное) исправление — разделить
`ReverseEngineerService.run` на две функции с разными инвариантами
(snapshot-for-compare без seed; write-to-codebase с seed) +
добавить `seed_deploy` флаг в конструктор. Техдолг.

## Key decisions & constraints (Phase 15.5.2)

- **Explicit utility > hidden fix.** Compromised: вместо глобального
  рефакторинга RE (флаг `seed_deploy`) — отдельная команда
  `db-pm deploy init-service-schema`. Минимальный риск (не ломает
  существующую RE-логику), явный шаг для пользователя (`на пустой БД:
  сначала init-service-schema, потом deploy apply`).
- **`adapter.get_database_structure()` — единственный источник правды**
  о реальном состоянии target-БД при bootstrap. Compare-snapshot
  нельзя использовать (он искажён phantom-seed из RE).
- **Идемпотентность через `CREATE … IF NOT EXISTS`** — повторное
  выполнение безопасно; регрессия `changed=False` в результате.
- **Один объект = один `execute_script` call** — при ошибке на второй
  таблице первая уже создана и персистентна; в ошибке — имя проблемной
  таблицы.

## Как использовать deploy init-service-schema

Перед первым `deploy apply` на свежей БД:

```bash
unset SSL_CERT_FILE REQUESTS_CA_BUNDLE CURL_CA_BUNDLE
db-pm deploy init-service-schema \
  --target-connection-file connections/local-PG-18_DB__cis_zup_dev_U_postgres.yaml

# Затем:
db-pm deploy apply \
  --dir "C:/repos/reksoft/locomoko/lm_hrdo_2/src/Postgres/cis_zup" \
  --target-connection-file "connections/local-PG-18_DB__cis_zup_dev_U_postgres.yaml" \
  --output-dir "C:/YandexDisk/Yandex.Disk/LM.HRDO-2.DEV/02_workitem/.../deploy_artefact" \
  --include-drops --no-rehearsal --keep-rehearsal-db
```

Команда идемпотентна:
- Empty БД → создаёт `__deploy` schema +3 таблицы → exit 0.
- Уже инициализированная → no-op summary → exit 0.
- Ошибка подключения или SQL → exit 2 с понятным сообщением.
