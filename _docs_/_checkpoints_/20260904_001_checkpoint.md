## Key decisions & constraints (Phase 15.5)

- **Multi-level defence против PG round-trip различий.** Каждый слой pipeline
  делает свою часть канонизации: `normalize_sql` (text-casts), `columns.py`
  (type-aliases + default-comp), `comparator` (column-diff fallback). Это
  симметрично архитектуре less-is-more: каждое преобразование — narrow scope,
  нет одной гигантской «канонизирующей всё» функции.
- **Conservative.** Phase 15.5.3 канонизирует **только** `CAST(<string> AS TEXT)`
  и `<string>::text`. Phase 15.5.4 канонизирует только семейства serial/int/float.
  Numeric/identifier cast **не** трогаются. Backup: `columns_unavailable=True`
  → не доверяем column-diff, остаёмся на hash (fail-safe).
- **Hash-канонизация хрупкая.** Альтернатива — YAML-diff (BACKLOG). Текущие
  фиксы — patch, не решение.
- **`sql_hash` остаётся coarse-signal.** Phase 15.5.5 не пытается
  канонизировать типы в `normalize_sql` (там много edge-кейсов — mixed case,
  qualified names). Вместо этого — column-diff как второй signal.

## **To resolve in next session**

### Приоритет 1 — Phase 15.5.6: `keep-target-dir` для отладки (BACKLOG `db900be`)

**Проблема:** target-side snapshot пишется в `tempfile.mkdtemp(prefix="dbpm_compare_target_")`,
затем удаляется (`shutil.rmtree`). Невозможно после analyze посмотреть, что
**именно** RE прочитал из БД.

**Решение (предложенное пользователем, BACKLOG `db900be`):**

1. Добавить опцию `--keep-target-dir` для `db-pm compare run` и
   `db-pm deploy analyze`.
2. После RE `temp_root` копируется в `<output_dir>/target/`
   (для DB-стороны) или `<output_dir>/source/` (для DIR).
3. После переноса — `shutil.rmtree(temp_root)` (или `--keep`).

**Зачем приоритет 1:** следующий false-positive (а он придёт — PG-эквивалентностей
осталось много, см. LESSONS §64 уроки 2 и 4) потребует аналогичной
диагностики. Без этой опции — каждый раз подключаться к БД самописными
скриптами (как делали для cis_zup).

**Объём:** ~1 час реализации + 1–2 теста.

### Приоритет 2 — Phase 15.5.6-arch: YAML-diff (BACKLOG)

После 3 фиксов подряд hash-канонизация явно хрупкая. Архитектурное решение —
YAML-сравнение source vs target через структурный diff по полям.
См. `_docs_/_tasks_/BACKLOG.md` §P3 «YAML-сравнение source vs target вместо

### Приоритет 3 — другие PG-эквивалентности (LESSONS §64 урок 4)

Каждый новый false-positive потребует:
1. Новый mapping в `_TYPE_ALIASES` ИЛИ `_canonicalize_text_casts` ИЛИ новая
   default-comp rule.
2. + regression-тест.
3. + LESSONS entry (продолжение §64).

Возможные классы (если столкнёмся):
- `VARCHAR(n)` vs `TEXT` (если `n > max` или наоборот).
- `TIMESTAMP` vs `TIMESTAMP WITHOUT TIME ZONE`.
- Auto-generated constraint names (`tablename_pkey` vs кастомные).
- `NUMERIC(p,s)` precision-only difference (если PG округлил precision).

### Приоритет 4 — auto-update existing codebases

**Backlog item:** кодовая база cis_zup по-прежнему содержит `DEFAULT (...) AT TIME ZONE 'utc'`
и `serial4` (без явного `NEXTVAL`). После Phase 15.5 эти формы **канонизируются
hash-wise**, но **физические файлы** не изменились. Если пользователь
когда-нибудь захочет выкинуть hash-diff полностью и перейти на YAML — стоит
один раз прогнать по codebase скрипт типа
`db-pm migrate-codebase-to-canonical-forms` (Phase 16+, не блокирует).
