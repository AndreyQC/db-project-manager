## Проблема

В кодовых базах встречаются объекты, чей DDL содержит значения, привязанные к
конкретной среде/воркспейсу. Главный пример — внешние таблицы Greenplum:

```sql
LOCATION ('pxf://ods_hn_zup."Account_groups"?PROFILE=JDBC&SERVER=ods_zup&QUOTE_COLUMNS=true')
```

`LOCATION` может меняться и содержать разное (сервер PXF, схема HDFS и т.д.).
Кроме того, параметризованы могут быть **имена схем**: деплой из dev уходит в
разные схемы — по схеме на каждый воркспейс (в `hrdo_ods` это
`ods_hn_zup_masked`, `ods_hn_trade_zup_masked`). Сейчас такие значения зашиты
в файлы — деплой одной кодовой базы в другую БД невозможен без ручной правки.

В db-pm механизма подстановки параметров **нет** (проверено 2026-10-27:
единственный «паттерн значения» — крипто-формат `crypto__<ENV>__<ciphertext>`).

## Согласованные решения (диалог 2026-10-27)

1. **Плейсхолдер в теле SQL**: `{{param_name}}` (jinja-стиль — не конфликтует
   с `$` в PG и `&` в GP; в живом DDL почти не встречается).
2. **Файл параметров**: `dbpm.params.yaml` в корне кодовой базы, рядом с
   `dbpm.manifest.json`. Имя зафиксировано пользователем. Секция
   `parameters:` со скалярными значениями.
3. **Манифест не трогаем**: `dbpm.manifest.json` генерируется инструментом
   (перегенерируется при RE) — ручной файл параметров переживает
   перегенерацию без требований «сохранять чужие секции».
4. **Крипта**: значение вида `crypto__<ENV_VAR>__<ciphertext>` расшифровывается
   готовым механизмом (`infrastructure/crypto/crypto_util.py`, Fernet,
   ключ `ENVOS_CRYPTO_01`); обычное значение берётся как есть. Расшифровка —
   на последнем шаге разрешения значения.
5. **Цепочка приоритетов**: `--param` (CLI) → `params:` из
   `connections/*.yaml` → `parameters:` из `dbpm.params.yaml`.
6. **Момент подстановки**: пре-процессинг текста **до парсинга** — граф,
   validate и apply работают уже на развёрнутых именах (иначе параметризация
   имён схем ломает `object_key` и рёбра).
7. **Fail-fast**: неразрешённый плейсхолдер валит `graph build` /
   `deploy validate` / `deploy apply` с явным списком неразрешённых параметров
   и файлов, где они встретились (решение пользователя). Тихая подстановка
   опасна: неразрешённое имя схемы молча испортит граф.
8. **Compare между средами** с разными значениями параметров (renamed-картина
   `object_key`) — осознанно на MVP принять, решение позже (запись в BACKLOG).

## Эскиз (как согласовано)

`dbpm.params.yaml` (корень кодовой базы):

```yaml
# Параметры подстановок для деплоя. Плейсхолдер в SQL: {{param_name}}.
# Значение может быть криптой crypto__<ENV_VAR>__<token> — расшифровывается
# тем же механизмом, что пароли подключений (ключ ENVOS_CRYPTO_01).
parameters:
  pxf_server: ods_zup
  hdfs_schema: ods_hn_zup
  svc_password: crypto__ENVOS_CRYPTO_01__gAAAAABm...
```

SQL-файл:

```sql
LOCATION ('pxf://{{hdfs_schema}}."Account_groups"?PROFILE=JDBC&SERVER={{pxf_server}}&QUOTE_COLUMNS=true')
```

Переопределение под конкретную базу — новая секция в `connections/*.yaml`
(рядом с `password`, который уже умеет крипту; модель `ConnectionConfig`):

```yaml
name: hrdo_ods_prod
params:
  pxf_server: ods_zup_prod
```

CLI (для разовых прогонов и CI):

```bash
db-pm deploy apply --dir ... --connection-file ... --param pxf_server=ods_zup_prod
```

## Этапы (черновик — детализировать при планировании фазы)

1. **Resolver**: загрузка `dbpm.params.yaml` + `params:` подключения + `--param`;
   разрешение по цепочке приоритетов; крипта последним шагом; fail-fast со
   списком неразрешённых.
2. **Пре-процессинг**: подстановка `{{param}}` при чтении SQL-файлов перед
   парсингом (`graph build` и далее по цепочке). Autodoc-заголовки из
   подстановки исключить (см. открытые вопросы).
3. **CLI**: `--param name=value` (повторяемый) в `graph build`,
   `deploy validate`, `deploy apply`; опционально `db-pm params init`
   (заготовка файла).
4. **ConnectionConfig**: поле `params: dict[str, str]` (+ крипта через
   существующий decrypt-механизм при загрузке).
5. **Тесты**: unit (резолвер, приоритеты, крипта, fail-fast) + integration
   (деплой кодовой базы с `{{param}}` в чистую PG).
6. **Потребитель `hrdo_ods`**: параметризовать LOCATION внешних таблиц,
   прогнать деплой в две схемы без правки файлов.

## Открытые вопросы плана (решить на этапе детализации)

- **Плейсхолдеры в теле vs autodoc**: autodoc-заголовок содержит
  `object_schema`/`object_key` с уже развёрнутыми именами (RE пишет реальные
  значения). Если параметризуется имя схемы в теле (`CREATE EXTERNAL TABLE
  {{schema}}.…`), возникает рассинхрон с identity из autodoc. MVP — autodoc
  не подставлять и не трогать; параметризацию имён схем для identity либо
  отложить, либо решить отдельным механизмом (RE per-workspace).
- **RE/compare с плейсхолдерами**: сравнение кодовой базы (плейсхолдеры) с БД
  (развёрнутые значения) — связано с бэклог-записью про renamed-картину.
- **Синтаксис CLI**: экранирование значений с `=` внутри; `--param-file`
  как опция — оценить.
- **sql_hash**: подстановка меняет текст до хэширования → hash объектов с
  параметрами зависит от значений; в рамках одного набора значений
  консистентен — зафиксировать в LESSONS.

## Критерии приёмки

- Кодовая база с `{{param}}` деплоится в две разные БД/схемы без правки
  SQL-файлов (только значения параметров).
- Криптованное значение расшифровывается при деплое; открытый текст секретов
  не попадает в логи/планы/отчёты (проверить явно).
- Неразрешённый параметр → ошибка со списком параметров и файлов (fail-fast).
- Регресс db-pm: unit-тесты зелёные, ruff clean.

## Риски

- Подстановка до парсинга — точка входа для всех потребителей файлов
  (GUI, MCP, compare): менять в одном месте (загрузчик/парсер), а не в каждом
  действии.
- Секреты в значениях параметров: не логировать разрешённые значения,
  маскировать в отчётах.
- Существующие кодовые базы без плейсхолдеров не затронуты (нет `{{...}}` —
  нет подстановки).
