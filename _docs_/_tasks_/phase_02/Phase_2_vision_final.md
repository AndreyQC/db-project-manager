## 0. Почему это важно

Инструмент для инженерии структуры БД уровня SSDT (Microsoft SQL Server Data Tools), но **open-source и для PostgreSQL/Greenplum** — такого практически нет. Существующее (Liquibase, Flyway, sqitch, pg-structure) покрывает часть задач, но ни одно не даёт: реверс-инжиниринг в типизированное дерево файлов + autodoc-метаданные + граф зависимостей + валидируемый деплой на пустую БД + дифф/миграции — в одном пакете с CLI и UI.

Phase 2 закрывает два ключевых сценария из видения (`002_idea.md`):
1. **Валидация артефактов** — деплой кодовой базы на пустую временную БД для проверки, что всё собирается.
2. **Граф зависимостей** — построение и хранение графа объектов для последующего анализа (в т.ч. внешними инструментами).

## 1. Сценарий A — Деплой валидации (Validation Deploy)

### 1.1. Суть
На сервере, к которому есть права `CREATEDB`, разворачиваем кодовую базу (каталог SQL-файлов) в **пустую временную БД**, чтобы убедиться, что весь скрипт собирается без ошибок. Это базовая «дымовая проверка» для CI/CD и для разработчика перед коммитом.

### 1.2. Имя целевой базы
- Формат: `<prefix>_<YYYYMMDDTHHMMSS>`, например `myapp_20260718T143022`.
- **`<prefix>`** — по умолчанию имя корневого каталога кодовой базы, sanitized (`lowercase`, `[a-z0-9_]`); переопределяется через `--prefix`. **[Решение Q5]**
- **Timestamp берётся с сервера БД**, а не с клиента:
  - В CI время раннера может расходиться с БД (NTP drift, разные часовые пояса).
  - Уникальность имени гарантируется на стороне сервера.
  - Используем `SELECT to_char(now() AT TIME ZONE 'UTC', 'YYYYMMDD"T"HH24MISS')` (UTC для детерминизма и чтобы избежать проблем с DST).
- Суффикс должен быть гарантированно уникален: если БД с таким именем уже существует (коллизия в ту же секунду), повторяем запрос timestamp или добавляем суффикс-счётчик.

### 1.3. Проверка прав
**До** создания БД — пробный запрос:
```sql
SELECT usecreatedb FROM pg_user WHERE usename = current_user;
-- и для надёжности: ролей
SELECT EXISTS(SELECT 1 FROM pg_roles WHERE rolname = current_user AND rolcreatedb);
```
Если `usecreatedb = false` → немедленная осмысленная ошибка: «У пользователя X нет прав CREATEDB. Validation deploy требует создания временной БД. Обратитесь к DBA или используйте сценарий B (миграции).» Без этой проверки пользователь получит невнятный сбой посередине деплоя.

### 1.4. Порядок деплоя — топосортировка + фильтр
1. Прочитать кодовую базу (каталог SQL-файлов), распарсить autodoc-блок каждого файла → получить vertices (объекты) с метаданными.
2. Построить edges (зависимости) — см. §2.
3. **Отфильтровать** vertices/edges по `project.build: true` (из autodoc). **[Решение Q8]** Объекты с `build: false`:
   - **в граф попадают** (видны зависимости);
   - **при deploy validate — пропускаются**. Это даёт гибкость (отключить объект без удаления файла).
4. Топосортировка: schema → sequence → table → index → constraint → view → materialized_view → function → procedure → policy → grant (приоритеты из POC).
5. Последовательное выполнение скриптов — режимы по **[Решению Q4]**, см. §1.7.
6. Cleanup временной БД — по **[Решению Q3]**, см. §1.6.

### 1.5. Будущее (не Phase 2)
- Создание и прогон тестов процедур на задеплоенной БД (data quality / smoke tests).
- Параллелизация независимых веток графа для ускорения деплоя.

### 1.6. Cleanup временной БД **[Решение Q3]**
- **CLI:** по умолчанию временную БД **УДАЛЯТЬ** (cleanup); флаг `--keep-db` для отладки. Cleanup в `finally`, чтобы не осталось БД даже при ошибке.
- **GUI:** оставить пользователю выбор — чекбокс «оставить БД для отладки» (по умолчанию выключен, т.е. тоже cleanup). Удобно при интерактивной отладке.
- Обоснование: проверочный стенд, сервер мусорить не должны; оставить можно явно в любом интерфейсе.

### 1.7. Транзакционность и стратегия ошибок **[Решение Q4]**
- Режим выполнения — **пообъектно** (DDL вроде `CREATE DATABASE` / `CREATE SCHEMA` в PG часто не откатываются в одной транзакции — единая транзакция технически невозможна для полного деплоя).
- **Стратегия по типам объектов (уточнённое решение):**
  - **Схемы, последовательности, таблицы (ранние DDL):** при первой ошибке — **fail-fast + немедленный cleanup базы**. Продолжать нет смысла: оставшиеся объекты зависят от упавшей схемы/таблицы, получим каскад нерелевантных ошибок.
  - **Представления, функции, процедуры (поздние объекты):** имеет смысл **пообъектный лог** — флаг `--continue-on-error` собирает все ошибки за один прогон (одна упавшая процедура не должна маскировать остальные).
- Флаг CLI `--continue-on-error` управляет поведением для поздних объектов; для ранних DDL cleanup выполняется всегда при ошибке.
- Отчёт: «объект N (`schema.table`) упал с ошибкой X (файл `path/to/file.sql`, строка K)».

### 1.8. CLI
```
db-pm deploy validate \
    --dir <codebase-dir> \
    --connection-file <conn.yaml> \
    [--prefix <name>] \
    [--keep-db] \
    [--continue-on-error]
```
- `--keep-db`: не удалять временную БД (для отладки).
- `--continue-on-error`: для views/functions/procedures — продолжать и собрать все ошибки.
- Возвращает код 0 (успех) / ненулевой (с указанием упавшего объекта).

## 2. Граф зависимостей

### 2.1. Источник данных
Граф строится **по кодовой базе** (каталогу SQL-файлов), не по живой БД — так он отражает актуальное состояние репозитория и доступен офлайн (в CI без подключения). Источник правды — autodoc-блок в каждом файле (`object_key`, `object_type`, `object_schema`, `object_name`).

### 2.2. Рёбра (зависимости)
Типы зависимостей (из POC `dflw_parser_pg_sql`, переработать):
- `REFERENCES_BY` — внешний ключ (FK → referenced table).
- `PROVIDE_DATA_TO` — `SELECT`/`JOIN` из view, matview, function.
- `CHANGE_DATA_IN` — `INSERT`/`UPDATE`/`MERGE`/`DELETE`/`TRUNCATE` в function/procedure/trigger.
- `SEQUENCE_NEXTVAL_IN` — `nextval(seq)` в default/function.
- (опц.) `DEPENDS_ON` — `CREATE ... Requires` для расширений.

### 2.3. Способ извлечения **[Решение Q1]**
- **Phase 2 (MVP):** перенос парсера из POC (`dflw_parser_pg_sql`) с исправлениями критичных багов (недостижимые `elif`, O(n²), дедупликация рёбер). Быстрый старт, рабочая валидация деплоя раньше.
- **Phase 2+ (улучшение):** `sqlglot` как более точный AST-бэкенд за **интерфейсом парсера** (сменный бэкенд).
- **Важный архитектурный нюанс:** парсер проектируется как **generic-интерфейс** (`ObjectGraphParser`), не завязанный на SQL, потому что **тот же формат файлов+autodoc будет переиспользован для других типов проектов** — Informatica Power Center, Apache Airflow DAGs и т.п. (у каждого — свой concrete-парсер, реализующий общий контракт: «прочитать каталог файлов → вернуть vertices+edges»).
- Обоснование решения: быстрый старт на проверенном коде; sqlglot — улучшение, не блокер; generic-интерфейс = переиспользование вне SQL-проектов.

### 2.4. Хранение графа — `.dbm_graph/` **[Решение Q2]**
Каталог **внутри кодовой базы** (рядом с SQL-файлами):
```
<codebase-dir>/
├── bookings/
│   ├── tables/table aircrafts.sql
│   └── ...
└── .dbm_graph/
    ├── vertices.json     # список объектов (метаданные из autodoc)
    ├── edges.json        # зависимости
    ├── graph.json        # готовый граф (vertices + edges в одном файле для portability)
    ├── meta.json         # версия формата, когда построен, хэш кодовой базы
    └── (опц.) graph.graphml  # для импорта во внешние инструменты
```

**Решение по git:** `.dbm_graph/` **игнорируется целиком** (в `.gitignore`). Граф детерминированно строится из кодовой базы за секунды; хранить его в git = постоянные шумные диффы. `meta.json` тоже генерируемый; согласованность граф↔код проверяется командой `db-pm graph validate`, а не lock-файлом. Всегда можно перестроить.

- **Перегенерация:** при изменении SQL-файлов (по хэшу/mtimes) или явно по команде.
- **Формат:** JSON с человекочитаемой структурой (не минифицированный) — для diff-ability и инспекции.

### 2.5. CLI
```
db-pm graph build --dir <codebase-dir>           # построить, записать в .dbm_graph/
db-pm graph export --dir <codebase-dir> \
    --format json|graphml|dot \
    [--output <file>]                              # экспорт в стандартный формат
db-pm graph show --dir <codebase-dir> \
    --object <object_key>                          # показать зависимости объекта
db-pm graph validate --dir <codebase-dir>          # проверить: циклы, висячие ссылки
```

### 2.6. Интеграция с деплоем (Scenario A)
`deploy validate` использует тот же граф: `graph build` (если устарел) → `toposort` → деплой. Граф — переиспользуемый артефакт между всеми операциями, а не внутренняя деталь.

### 2.7. Визуализация **[Решение Q7]**
В Phase 2 — **только экспорт** (json/graphml/dot) для внешних инструментов. GUI-просмотр графа в нашем приложении не делаем: у тебя уже есть Tauri-приложение по анализу графов, которое примет экспортированный файл. (Отрисовка графа в Qt — отдельная нетривиальная задача, оставлена на будущее.)

## 3. Сценарий B — Миграции на БД с данными (ВЫНЕСЕН В ОТДЕЛЬНУЮ ФАЗУ)

### 3.1. Почему отдельная фаза
Деплой на DEV/TST/PRD, где уже есть данные, принципиально сложнее:
- Нужна модель текущей БД (полный reverse-engineering, как в Phase 1).
- Дельта (diff) между кодовой базой и схемой: новые/удалённые/изменённые объекты.
- Для таблиц часто недостаточно DROP+CREATE (потеря данных) — нужен ALTER-план.
- Pre/post-deploy скрипты, учёт наличия данных (sampling, `pg_class.reltuples`).
- Это полноценный engine миграций — объём отдельной фазы.

### 3.2. Что фиксируем на будущее (не реализуем в Phase 2)
- `db-pm deploy migrate` — деплой дельты на существующую БД.
- `db-pm diff --dir <dir> --connection-file <conn.yaml>` — сравнение кодовой базы и живой схемы.
- Генерация ALTER-скриптов с учётом данных (пометки «ручная миграция» для разрушительных изменений).
- Pre/post-deploy hooks.

> В Phase 2 не делаем. Фиксируем как Phase 3 в roadmap (обновить `003_roadmap_migration.md`).

## 6. Метрики приёмки Phase 2

- `db-pm graph build` на каталоге `samples/aviasales_medium` строит корректный граф (без циклов, с ожидаемыми зависимостями) и пишет в `.dbm_graph/`.
- `db-pm graph validate` корректно находит циклы и висячие ссылки (тест на синтетическом цикле).
- `db-pm graph export --format graphml` создаёт файл, открываемый в Gephi/yEd и в твоём Tauri-приложении.
- `db-pm deploy validate --dir ... --connection-file ...` разворачивает образец на пустой временной БД на тестовом PostgreSQL; успех = код 0, fail = код ≠ 0 с указанием упавшего объекта.
- Проверка прав CREATEDB: без прав — осмысленная ошибка до попытки создания БД.
- `project.build: false` объекты пропускаются при деплое, но присутствуют в графе.
- Стратегия ошибок (§1.7): упавшая схема → cleanup; упавшая процедура с `--continue-on-error` → отчёт продолжается.
- `.dbm_graph/` в `.gitignore`.
- Интеграционные тесты (testcontainers) покрывают graph build + deploy validate.
- CLI и GUI (если добавляется GUI-шаг) работают на одном application-слое.

## 8. Почему open-source SSDT-аналог для PG/GP востребован

(Фиксация мотивации для будущей README.)

- **SSDT** — зрелый, но проприетарный и только для MSSQL.
- **Liquibase/Flyway/sqitch** — focused на миграциях, не на целостной инженерии структуры (реверс-инжиниринг в файлы + граф + валидация).
- **DBeaver** — IDE для ad-hoc работы, не pipeline-инструмент.
- **Наш пакет** — CLI-first (CI/CD-native), реверс-инжиниринг в типизированное дерево файлов с autodoc, граф зависимостей как first-class артефакт (с экспортом в Tauri-приложение и др.), валидируемый деплой, и eventual migrations — open-source. Заполняет нишу между «raw SQL-скрипты» и «тяжёлыми проприетарными SSDT».

Это сильный фундамент для open-source-сообщества PG/GP-инженеров. Дополнительно: generic-интерфейс парсера открывает путь к поддержке не-SQL проектов (Informatica, Airflow) в будущем.
