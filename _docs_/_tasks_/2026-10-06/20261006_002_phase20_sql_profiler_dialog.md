## Открытый вопрос (USER_INPUT, 2026-10-06 — вопрос пользователя)

> Если статистика по таблицам не заполнена, то как мы будем проверять
> [размер таблицы для порога], будем ли запускать ANALYZE на больших
> таблицах и так далее?

### Контекст проблемы

- Без статистики `pg_class.reltuples` = -1 (или 0) — порог «полный проход
  vs сэмпл» по строкам не работает. На dev GP 275 таблиц без статистики
  (spike, `gp_toolkit.gp_stats_missing`).
- `ANALYZE` — write против каталога (`pg_statistic`): наш RO-backstop
  Phase 19 его структурно не пропустит, а исполнение вне RO-транзакции
  сломало бы контракт read-only и меняло бы поведение планировщика для
  всех пользователей БД (side-effect, которого профайлер делать не должен).
- Сэмпл `random() < p` не уменьшает IO (скан всё равно полный) — он удешевляет
  только агрегаты/перелив данных; значит «дорогой» путь не так дорог, и точная
  оценка строк для него менее критична.

### Варианты

1. **Порог по размеру на диске; ANALYZE сами не запускаем никогда.**
   (Recommended) Порог «полный проход vs сэмпл» — по
   `pg_total_relation_size()` (точный, статистики не требует, работает и для
   heap, и для AO-таблиц GP; на мастере GP возвращает суммарный размер по
   сегментам). `reltuples` — вспомогательный сигнал, когда статистика есть.
   Таблицы без статистики — не проблема: порог в байтах от неё не зависит.
   Для доли сэмпла без `reltuples` — константа `default_sample_fraction`
   (например 0.01) в блоке `profiling:`. В профиле поле `stats_fresh: false`
   + совет «запустите ANALYZE вручную» (инструмент не делает).
2. **ANALYZE по явному opt-in.** Отдельный гейт (`profiling.allow_analyze`),
   исполнение вне RO-транзакции, только по явной команде пользователя.
   Даёт точную статистику, но: write-путь в «профайлере», нагрузка на
   кластер (AO-таблицы — долго), изменение планов запросов у всех — по
   сути отдельная фича.
3. **Требовать статистику.** Таблицы без статистики пропускаем с
   предупреждением «сначала ANALYZE». Простое поведение, но на реальном dev
   (275 таблиц) профайлер сразу упирается в стену — половина БД
   непрофилируема.

### ИИ-рекомендация

Вариант 1. Дополнительно: `full_size_threshold_bytes: 1073741824` (1 GiB)
в блоке `profiling:` вместо строкового порога; `sample_rows` сохраняется
для случая, когда статистика есть; при отсутствии статистики доля сэмпла =
`default_sample_fraction`. `gp_toolkit.gp_stats_missing` — источник
предупреждений, не действий.

## Решение

**Вариант 1** — принят как рабочий (2026-10-06):

- Порог «полный проход vs сэмпл» — по `pg_total_relation_size()`,
  настройка `full_size_threshold_bytes` (default 1 GiB). Статистика для
  порога не нужна вовсе (heap и AO-таблицы GP, суммарный размер по
  сегментам на мастере).
- `reltuples` — вспомогательный сигнал: из него считается доля сэмпла
  `p = sample_rows / reltuples`. Без статистики — `default_sample_fraction`
  (default 0.01).
- **ANALYZE инструмент не запускает никогда**: write против каталога
  не проходит RO-backstop, меняет планы у всех пользователей БД. В профиле —
  `stats_fresh: false` и текстовый совет «запустите ANALYZE вручную»;
  `gp_toolkit.gp_stats_missing` — источник предупреждений, не действий.

Пометка (обновление 2026-10-06): пользователь подтвердил решение —
«полностью согласен со стартом фазы двадцать». Вариант 1 зафиксирован как
утверждённый, фаза стартовала. План фазы синхронизирован (порог
reltuples → байты); final 20261006_001 не правится (история решений).

## 4. Приёмка: вызов profile_tables из командной строки (2026-10-06)

### Запрос пользователя

Показать пример, как вызывать MCP-инструмент `profile_tables` из командной
строки, по GP-подключению, использованному для тестирования
(`IVSD00258.reksoft.com_GP__DB__cis_zup_gp_dev__U_gpadmin`).

### Что сделано

- В файл подключения добавлен блок (гейт фазы; без него инструмент
  отклоняет вызов до первого запроса к БД):

  ```yaml
  profiling:
    enabled: true
  ```

- Вызов через stdio JSON-RPC (репозиторий, Git Bash):

  ```bash
  printf '%s\n' \
    '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"cli-demo","version":"0.0.0"}}}' \
    '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
    '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"profile_tables","arguments":{"connection":"IVSD00258.reksoft.com_GP__DB__cis_zup_gp_dev__U_gpadmin","tables":["src_ods_hn_trade_zup.ext_department"]}}}' \
    | uv run db-pm-mcp 2>/dev/null
  ```

- Строки stdin: 1) `initialize` (рукопожатие), 2) `notifications/initialized`
  (без ответа), 3) `tools/call` — сам вызов; `connection` = имя yaml-файла
  из `connections/` без расширения, `tables` — список `schema.table`.
- Ответ: последняя строка stdout; `result.content` содержит по одному
  блоку `text` на каждую таблицу (JSON `TableProfile` целиком) — FastMCP
  сериализует список по элементам.

### Результат живого прогона

`src_ods_hn_trade_zup.ext_department`: rows=0 (оценка reltuples=1 —
расхождение видно честно), size=98304B, stats_fresh=true, 10 колонок,
759 мс; `isError: false`.

### Примечания

- `2>/dev/null` прячет stderr-логи сервера (в протоколе stdout только
  JSON-RPC); полный аудит — `logs/mcp_queries.log` (Phase 19.1).
- В реальном MCP-клиенте (ZCode/OpenCode, конфиги в README раздела MCP)
  handshake делает клиент: вызывающий просто передаёт `connection` и
  `tables`. Printf-вариант — для проверки из консоли/CI без клиента.

## 5. Квотированные имена таблиц (2026-10-06)

### Вопрос пользователя

Можно ли передавать список таблиц с именами в двойных кавычках?

### Ответ/решение

Было нельзя (кавычки трактовались как часть имени). Реализовано по правилам
идентификаторов SQL: `"My Schema"."My.Table"` — кавычки снимаются, `""` —
экранирование кавычки, точка внутри кавычек не делит имя, квотированная часть
сохраняет регистр, неквотированная фолдится в нижний (как планировщик).
Действует и в CLI (`db-pm profile --tables`), и в MCP (`profile_tables`) —
разбор общий (`parse_qualified`). Живой прогон на GP dev:
`--tables '"src_ods_hn_trade_zup"."ext_department"'` — OK.
Ограничение: запятая — разделитель списка, внутри квотированного имени
запятую не поддержать (в MCP список передаётся массивом — там ограничения нет).

## 6. Пример на списке таблиц (2026-10-06)

### Запрос пользователя

Прокачать пример вызова на списке таблиц.

### CLI (список через запятую, микс квотированных и обычных имён)

```bash
uv run db-pm profile IVSD00258.reksoft.com_GP__DB__cis_zup_gp_dev__U_gpadmin \
  --tables '"src_ods_hn_trade_zup"."ext_department",src_ods_hn_trade_zup.ext_cost_centers,src_ods_hn_trade_zup.ext_account_groups'
```

Результат: по строке сводки на таблицу + по JSON-файлу на каждую в
`reports/<connection>/` (3 профиля).

### MCP (tables — JSON-массив)

`tools/call profile_tables` с
`"tables": ["src_ods_hn_trade_zup.ext_department", "\"src_ods_hn_trade_zup\".\"ext_cost_centers\"", "src_ods_hn_trade_zup.ext_account_groups"]`
→ `isError: false`, 3 content-блока (по одному `TableProfile` на таблицу):
ext_department — 10 колонок / 777 мс; ext_cost_centers — 9 / 584 мс;
ext_account_groups — 7 / 753 мс. Второй элемент передан в кавычках внутри
JSON-строки — парсинг общий с CLI, кавычки снимаются.

### Зафиксированное поведение

- Fail-fast: не найденная таблица в списке останавливает прогон (exit 1),
  файлы за весь прогон не пишутся — большие списки предварительно
  проверять через MCP `list_objects`.
- Пустые таблицы (row_count=0): гистограммы/top-N не добираются — только
  nulls/distinct из каталога; осознанное поведение.

## 8. Машина без uv и без env-переменных (2026-10-06)

### Проблема пользователя

Перенести профайлинг на машину, где нельзя поставить uv и нельзя задать
переменные окружения с Fernet-ключами.

### Решения

1. **Портативный бандл `dbpm-portable/` (zip ~41 МБ)**: embeddable Python
   3.13.9 + site/ (проект + зависимости CLI/MCP, без GUI) + dbpm.cmd /
   dbpm-mcp.cmd. На целевой машине — ноль установки. Грабли: pywin32 в
   --target-каталоге требует ручной прописи путей (его .pth не работает);
   корпоративный прокси — unset SSL_CERT_FILE при сборке. Всё в .gitignore.
2. **Plaintext-пароли в connections/*.yaml** — поддержаны доменом с самого
   начала (незашифрованное значение проходит decrypt-проход как есть).
   В бандле все подключения переведены на открытые пароли (осознанный
   риск пользователя). Рабочий connections/ не тронут.
3. **Интерактивный ввод пароля в CLI** (новое): если env-ключ недоступен,
   `db-pm profile` запрашивает пароль (колбэк password_prompt через
   ConnectionStore; getpass на tty, stdin в конвейере; кэш по имени
   env-ключа — один ввод на ключ на запуск). `CryptoKeyMissing` в
   crypto_util; ошибки подключения заворачиваются в ProfilingError
   (без traceback). В MCP промпта нет — stdio занят протоколом.

### Проверено живьём из бандла без env-ключей

- plaintext-подключение → профиль собран (1 таблица);
- crypto-подключение + ввод пароля по stdin → один промпт, неверный пароль
  доходит до драйвера → чистая «Ошибка: не удалось подключиться...» (без
  traceback). Тесты: 1244 passed (+5), ruff чисто.
