## Запрос пользователя (2026-10-06)

Проанализировать возможность интеграции профайлера `pip install
ydata-profiling` в Db Project Manager: используя подключение, подключаться к
БД и выполнять профайлинг выбранных таблиц по списку. Дополнительно:
(1) просмотреть функционал библиотеки; (2) проверить, насколько она «опасна» —
может ли выполнять вредные запросы; (3) оценить возможности reverse-engineering
и создания профайлинга отдельно в нашем проекте. Приоритет — реализация под
Greenplum (GP 6 / Postgres).

## 1. Цель

По подключению из `connections/*.yaml` и списку таблиц
(`schema.table, ...`) построить профиль каждой таблицы (типы, пустые значения,
кардинальность, распределения, top-N частот, дубликаты и т.п.) и отдать его
в виде отчёта. Безопасно на больших таблицах и на GP 6.

## 2. Исследование библиотеки (2026-10-06, PyPI/доки)

- Актуальная версия `ydata-profiling` **4.18.4** (2026-04-22). В апреле 2026
  пакет **переименован в `fg-data-profiling`**; старое имя больше не получает
  исправлений. `requires-python >=3.10,<3.14` — Python 3.13 проекта
  поддерживается (numba разрешается в 0.61+, где есть поддержка 3.13).
- Вход — **pandas/Spark DataFrame**. Нативного SQL-коннектора нет: данные в
  библиотеку доставляем сами (`pd.read_sql` через SQLAlchemy, который уже
  есть в зависимостях). Чанковой загрузки из коробки нет — DataFrame целиком
  в памяти.
- Отчёт: типы колонок (visions), распределения, missing-статистика и
  correlation-матрицы (pearson/spearman/kendall/phik), дубликаты, warnings
  (constant/high-cardinality/skew), сэмплы первых/последних строк, HTML+JSON.
  Есть `minimal=True` (без correlations/interactions) для быстрого прогона.
- Зависимости тяжёлые: pandas, numpy, matplotlib, seaborn, statsmodels, scipy,
  numba, phik, wordcloud, imagehash, visions — ставятся только как optional
  extra (прецедент — extra `mcp` Phase 19).

## 3. Анализ безопасности («насколько опасна»)

Библиотека **не выполняет SQL сама и не пишет в БД** — вся работа на клиенте
над DataFrame. Единственные запросы к БД генерируем мы (`SELECT * ...`), т.е.
класс опасности = read-only SELECT. Реальные риски другие:

| Риск | Суть | Митигация |
|------|------|-----------|
| Полный скан | `SELECT *` на большой таблице: на GP — скан всех сегментов | Сэмплинг; агрегатный профайлинг (§4) |
| Выкачивание данных | Весь сэмпл течёт на мастер GP и в клиент | Ограничение размера сэмпла; агрегаты вместо сырых строк |
| Память клиента | Таблица в DataFrame целиком не влезает | Сэмпл фиксированного объёма; `minimal=True` |
| Ресурсы кластера | Долгие SELECT едят resource queue GP | statement_timeout + RO-транзакция (готовый backstop Phase 19) |
| Утечка данных | HTML-отчёт содержит сэмплы и top-значения (литералы данных) | Отчёты в gitignored-каталог; отключение samples; не пересылать |
| Качество отчёта | phik/correlations на высококардинальных строках — минуты-часы | `minimal=True` по умолчанию |

Вывод: «вредные запросы» невозможны по построению; опасность — ресурсная и
конфиденциальная, обе закрываются политикой подключения.

## 4. Greenplum 6 (PG 9.4) — ограничения и возможности

- Ядро GP 6.19.4 — **PG 9.4.26** (LESSONS §70): `TABLESAMPLE` (PG 9.5+) недоступен.
  Сэмплинг для GP — фильтр `WHERE random() < p` (скан полный, но фильтр
  локальный на сегментах) либо `ORDER BY random() LIMIT n` (дорогой, только
  для малых таблиц). Для PG 18 — нативный `TABLESAMPLE SYSTEM (p)`.
- Агрегаты в GP **параллелятся по сегментам** — SQL-агрегатный профайлер
  ложится на MPP-архитектуру идеально: считаем на сегментах, выкачиваем
  килобайты, а не гигабайты.
- `COUNT(DISTINCT)` в GP дорогой (redistribute). Наличие
  `approx_count_distinct`/HyperLogLog на целевом кластере — **проверить
  живьём**; fallback — точный `COUNT(DISTINCT)` на сэмпле.
- `pg_stats` на мастере даёт null_frac, n_distinct, most_common_vals,
  histogram_bounds почти бесплатно, но валидно только при свежем ANALYZE;
  свежесть проверяется через `gp_toolkit` (список админ-схем — LESSONS §71).

## 5. Варианты реализации

| | A. Интеграция ydata-profiling | B. Собственный SQL-профайлер | C. Гибрид |
|---|---|---|---|
| Как | сэмпл → `pd.read_sql` → `ProfileReport` → HTML | агрегатные запросы (count/nulls/distinct/min-max/top-N/перцентили/гистограмма) → JSON → свой HTML (jinja2 уже есть) | B как ядро; опционально «детальный отчёт» — сэмпл → ydata `minimal` → HTML |
| GP 6 | сэмплинг костылём, данные текут на клиента | нативно (MPP-агрегаты) | нативно |
| Зависимости | тяжёлые (extra) | ноль новых | тяжёлые — опционально |
| Объём кода | мало | средне (генератор SQL + рендер) | средне + тонкая обвязка |
| MCP/GUI переиспользование | сложно (нужен pandas) | да — JSON-профиль везде | да |
| Опасность | ресурсная (см. §3) | минимальная | управляемая |

**Рекомендация ИИ:** вариант **C**, поэтапно: сначала ядро B (SQL-профайлер —
он же источник данных для CLI/GUI/MCP), затем опциональная обвязка A для
«красивого» HTML по сэмплу. Reverse-engineering отчёта ydata: переносим
набор метрик в SQL-агрегаты, а не код библиотеки.

## 6. Архитектурный эскиз (C)

| Concern | Path (новое) | Note |
|---------|--------------|------|
| Модели | `domain/profiling.py` | TableProfile, ColumnProfile (pydantic, как QueryResult) |
| SQL-генератор | `infrastructure/profiling/sql_builder.py` | ветка `_is_greenplum` по образцу адаптера (LESSONS §70) |
| Сервис | `application/profiling_service.py` | список таблиц → план запросов → adapter.run_query в RO-транзакции + statement_timeout |
| CLI | `presentation/cli/` команда `profile` | `db-pm profile <connection> --tables schema.table,... --rows-sample N` |
| Отчёты | `reports/<connection>/<schema>.<table>/` | JSON всегда; HTML — при extra; каталог в .gitignore (PII) |
| Политика | блок `profiling:` в connections/*.yaml | enabled + sample_rows + timeout (по образцу блока `mcp:`) |

Пакет extra: `profiling = ["ydata-profiling>=4.18,<5"]` либо
`fg-data-profiling` (активное имя; requires-python проверить при реализации) —
см. USER_INPUT 6.
