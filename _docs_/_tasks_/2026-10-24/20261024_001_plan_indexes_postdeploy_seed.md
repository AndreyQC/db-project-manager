## Контекст

В проекте QR Память (PostgreSQL 18, схема из 7 доменных схем, 87 таблиц)
db-pm использовался для деплоя схемы через reverse engineering. Обнаружены
недочёты (задача 20261023_588 в проекте-потребителе): db-pm не знает объектов
`index` и `constraint`, ставит `trigger` раньше `function`, не выгружает
гранты и seed-данные.

Эта задача — фокус на двух аспектах, названных пользователем:

1. **Индекс как объект деплоя** — поддержка автономных `CREATE [UNIQUE]
   INDEX` в парсере, графе, RE и деплое; индексы живут внешне (отдельные
   файлы `<schema>/indexes/`), а не внутри скрипта создания таблицы.
2. **Засев данными постдеплойными скриптами** — наполнение справочников
   через механизм pre/post-deploy скриптов.

Остальные пункты 20261023_588 (`constraint`-объекты, порядок триггеров,
гранты) — отдельная работа, здесь не дублируются.

механизм готов. Основная кодовая работа — объект `index`.

## Почему индекс как внешний объект — правильная модель

1. **Это модель самого PostgreSQL.** `pg_dump` экспортирует CREATE TABLE
   (с PK/UNIQUE/FK-констрейнтами инлайн) + отдельные `CREATE INDEX`.
   Вторичный индекс нельзя валидно выразить внутри CREATE TABLE — «внешне»
   и есть канонический способ.
2. **Сейчас деплой тихо неполный.** `deploy validate` qr-проекта зелёный
   (448/448), но temp-БД без 123 индексов: план считает всё ок, а
   производительность источника не воспроизводится. compare дрейф тоже
   не покажет.
3. **Управляемость.** Отдельный объект = виден в графе (ребро index → table),
   участвует в deploy journal, можно точечно исключить/пересоздать, включить
   в дельта-план. Инлайн всего этого не даёт.
4. **Порядок и производительность.** Индексы после таблиц (`index: 3`) —
   уже в `TYPE_PRIORITIES`; в перспективе открывает оптимизацию «данные,
   потом индексы» (быстрее bulk-load).
5. **Цена умеренная** — порядка задачи CHProfiler: парсер + RE + тесты;
   деплой и сортировка уже готовы.

Что остаётся инлайном (и правильно): PK/UNIQUE-**констрейнты** внутри
CREATE TABLE — их неявные индексы часть определения таблицы. Внешне — только
автономные `CREATE [UNIQUE] INDEX …`.

## Цели

1. Проект QR Память деплоится в пустую БД так, что:
   - 123 существующих индекса попадают в граф и деплой (сейчас лежат
     в `<schema>/indexes/` вне графа);
   - справочники (`qr_ref.cities` — 1118 строк, и др.) наполняются
     постдеплойными скриптами без ручного прогона.
2. Универсально для db-pm (не только для qr): любой проект получает объекты
   `index` и конвенцию постдеплойного засева.

## Решения

### Часть A — индекс как объект деплоя (код db-pm)

1. **Парсер:** добавить `index` в `SUPPORTED_TYPES` и в
   `_CREATE_KEYWORD_TO_TYPE` (`CREATE [UNIQUE] INDEX … ON …`).
   Object_key: `type/index/name/<имя>` + `table` (индекс принадлежит
   таблице). Ребро `index → table` для топологической сортировки.
2. **RE:** выгрузка автономных индексов через `pg_get_indexdef` в
   `<schema>/indexes/index <name>.sql` с autodoc-заголовком — внешне,
   никогда не инлайн в табличный DDL. Существующие 123 файла qr-проекта
   сверить с форматом — парсер должен принять их без правок (или
   минимальными).
3. **Порядок деплоя:** `index` (3) после `table` (2) — уже готово в
   `TYPE_PRIORITIES`, изменений не требуется.
4. **Скоуп движков:** PG/GP. У CH data-skipping индексы живут внутри DDL
   таблицы и уже выгружаются как метаданные (`skip_indexes`) — CH не трогаем.
5. **Идемпотентность:** обычный `CREATE INDEX` (деплой в пустую БД);
   `CONCURRENTLY` для дельт на живых БД — отдельная будущая тема.

### Часть B — постдеплойный засев (код db-pm почти не нужен)

1. **Конвенция:** seed-данные → `__migrations/post/YYYY-MM-DD_NNN_seed_*.sql`,
   идемпотентность `INSERT ... ON CONFLICT DO NOTHING` (или `DELETE`+`INSERT`
   для перезаполняемых справочников — решить по каждому скрипту).
2. **Поведение:** первый `deploy apply` в чистую БД исполняет скрипт и пишет
   checksum в `__deploy.script_history`; повторный apply — SKIP. Изменение
   содержимого применённого скрипта — ERROR (новая версия = новое имя файла).
3. **Репетиция (`deploy validate`):** post-фаза исполняется и на temp-БД —
   засев проверяется на каждом validate автоматически. `__migrations/seed/`
   использовать не обязательно (он только для репетиции без пост-скриптов).
4. **Документация:** раздел в README/AGENTS проекта-потребителя (конвенция
   имён, идемпотентность, checksum-модель). Опционально — лист в `_docs_` db-pm.
5. **Замечание про CH:** `ScriptRunner` вызывает
   `get_script_history`/`record_script_execution`/`execute_script` — CH-адаптер
   всё реализует (Phase 5.6/6.1), но multi-statement `execute_script` на CH
   не проверялся на больших seed-объёмах — проверить отдельно, если засев
   понадобится на CH.

## Этапы

1. **Этап 1 — `index` как объект:** парсер (SUPPORTED_TYPES, keyword-маппинг,
   ребро к таблице), RE-выгрузка `pg_get_indexdef`, тесты unit.
2. **Этап 2 — приёмка формата на qr-проекте:** 123 ручных файла парсятся
   без правок (или минимальный фикс формата autodoc); `graph build`/`validate`.
3. **Этап 3 — постдеплойный засев:** конвертация сидов qr в
   `__migrations/post/`, проверка checksum-модели, документация.
4. **Этап 4 — сквозная приёмка на qr-проекте:** `deploy validate` (индексы
   создаются в temp-БД) + `deploy apply` в чистую БД + сверка `compare`.

Этапы 1–2 — код db-pm (коммиты `feat(...)`); этап 3 — в основном
проект-потребитель (коммиты там по их конвенциям); код и документы
не смешивать.

## Критерии приёмки

- [ ] `uv run pytest` зелёный (все существующие unit-тесты + новые), ruff clean.
- [ ] 123 индексных файла qr-проекта парсятся: `graph build` создаёт вершины
      `type=index` с ребром к таблице, `graph validate` без циклов.
- [ ] `deploy validate` qr-проекта создаёт индексы в temp-БД
      (объектный счётчик включает индексы).
- [ ] RE выгружает автономные индексы внешними файлами, не инлайн в DDL
      таблиц; PK/UNIQUE-констрейнты остаются в CREATE TABLE.
- [ ] `deploy apply` в чистую БД наполняет справочники через post-скрипты;
      повторный apply — SKIP по checksum (проверить в `script_history`).
- [ ] Регресс PG/GP/CH: существующие integration-тесты не сломаны.

## Риски

- **Новые вершины в графе:** 123 индекса добавят вершины и рёбра
  index → table; функциональные индексы (по выражениям) могут тянуть
  зависимости от функций — минимум ребро к таблице, зависимости от функций
  опционально. Проверять `graph validate` на qr-проекте.
- **Формат существующих файлов:** индексные файлы qr-проекта писались вручную
  до реализации парсера — autodoc-формат может не совпасть; сверить до кода.
- **Checksum-модель vs сиды:** правка наполнения справочника после применения
  требует нового имени файла — задокументировать, иначе ERROR на деплое.
- **Объём сидов:** 1118 городов одним statement-пачком — проверить
  производительность `execute_script` (PG — не проблема; CH — отдельная проверка).
- **Правки общего инструмента** затрагивают другие проекты — прогонять
  регресс `deploy validate` PG/GP/CH.
