# Conventions — правила ведения `-=tasks=-`

Регламент работы с задачами и документами фаз в каталоге `-=tasks=-`.
Цель — сохранять читаемую историю решений, разделять «черновик под обсуждение»
и «зафиксированный результат», а также делать документы самодостаточными.

---

## 1. Структура каталога

```
-=tasks=-
├── CONVENTIONS.md              # этот файл — регламент ведения
├── phase_00/                   # завершённая фаза (анализ/видение/roadmap)
├── phase_01/                   # завершённая фаза
├── phase_02/                   # активная фаза
│   ├── *_draft.md              # черновики под обсуждение
│   ├── *_final.md              # зафиксированные результаты
│   └── ...
└── phase_NN/                   # будущие фазы
```

- Каждая фаза — отдельный каталог `phase_NN` (двузначный номер, нумерация с нуля).
- Фаза считается **завершённой**, когда в ней нет `*_draft.md` и есть хотя бы один `*_final.md` (или план/отчёт).
- Этот файл (`CONVENTIONS.md`) — единственный документ верхнего уровня; всё остальное живёт внутри `phase_NN/`.

---

## 2. Жизненный цикл документа: `_draft` → `_final`

Любой документ, требующий согласования (видение, архитектура, план фазы, ключевые
решения), проходит два этапа.

### 2.1. Draft — черновик под обсуждение

Имя файла: `<Name>_draft.md` (например `Phase_2_vision_draft.md`).

Содержит:
- полную проработку темы;
- для каждого спорного/открытого вопроса — плейсхолдер `USER_INPUT` с рекомендацией ИИ.

**Формат плейсхолдера** (строго):

````markdown
### QN. <краткая формулировка вопроса>

<контекст, варианты (a)/(b)/(c), что выбрать>

```text
USER_INPUT:
<recommended by AI> <выбор> — <краткое обоснование>
```
````

Правила:
- ИИ всегда оставляет свою рекомендацию внутри `USER_INPUT` — пользователь
  не должен начинать с пустого места.
- Пользователь правит/подтверждает/добавляет `USER_INPUT` **прямо в `_draft.md`**.
- Пока есть незакрытые `USER_INPUT` (без явного ответа пользователя) — документ остаётся `_draft`.

### 2.2. Final — зафиксированный результат

Имя файла: `<Name>_final.md` (например `Phase_2_vision_final.md`).

Создаётся из `_draft.md` **после того, как все `USER_INPUT` закрыты**:
- блоки `USER_INPUT` раскрываются в решения (recommendation заменяется на
  финальный выбор пользователя, с сохранением обоснования);
- документ становится нормативным — на него ссылаются следующие шаги
  (план фазы, реализация, тесты).

Правила:
- `final` создаётся только после подтверждения всех ответов.
- После создания `final` соответствующий `draft` **не удаляется** — остаётся
  для истории обсуждения (видно, какие были альтернативы и почему отказались).
- Если в `final` нужно внести существенное изменение — открываем новый `_draft`
  (например `Phase_2_vision_v2_draft.md`), не правим молча `final`.

## 3. Именование документов

| Тип | Шаблон | Пример |
|------|--------|--------|
| Регламент | `CONVENTIONS.md` (только в корне `-=tasks=-`) | — |
| Анализ | `NNN_analysis_<topic>.md` | `001_analysis_existing_code.md` |
| Видение/архитектура | `<Name>_draft.md` → `<Name>_final.md` | `Phase_2_vision_final.md` |
| План фазы | `NNN_plan_phase_NN.md` | `001_plan_phase_01.md` |
| Отчёт/ретроспектива | `NNN_<topic>.md` | `001_retrospective.md` |

- `NNN` — трёхзначный порядковый номер внутри фазы (сортировка по имени).
- Файлы с суффиксом `_draft`/`_final` нумерации не имеют (это «живые» документы).
- Регистр: `snake_case`, английские имена (даже если текст внутри на русском).

---

## 4. Содержание документов

Каждый документ фазы должен быть **самодостаточным** — читаемый без контекста чата:

- **Заголовок H1** с темой и пометкой фазы.
- Вверху — блок «Контекст» со ссылками на связанные документы (относительные пути):
  ```markdown
  > Контекст:
  > - `-=tasks=-/phase_00/003_roadmap_migration.md`
  > - `LESSONS_LEARNED.md`
  ```
- Для видений/планов — явные разделы: цели, решения, метрики приёмки, риски.
- Дата в шапке (`Дата: YYYY-MM-DD`).
- Русский язык для основного текста; технические термины/идентификаторы — английские.

---

## 5. Правила коммитов

- Один логический документ — один коммит (например «создан draft vision Phase 2»).
- Сообщение коммита начинается с `docs(phase_NN):` и кратко описывает суть:
  ```
  docs(phase_02): add Phase 2 vision draft (graph + validation deploy)
  docs(phase_02): finalize Phase 2 vision (all USER_INPUT resolved)
  docs(phase_02): add detailed phase 2 plan
  ```
- `draft` и `final` коммитятся отдельно — так в `git log` видна история
  согласования (когда был предложен вариант, когда подтверждён).

---

## 6. Связь с реализацией

- `*_final.md` (видение) → источник для `NNN_plan_phase_NN.md` (детальный план).
- План фазы разбивается на шаги `S<номер>` (S10, S11, ...), продолжая нумерацию
  прошлой фазы (Phase 1 закончился на S9 → Phase 2 стартует с S10).
- Каждый шаг плана — потенциально отдельный коммит реализации (`feat(...)`,
  `fix(...)`); документы и код не смешивать в одном коммите.

---

## 7. Когда правило draft→final НЕ обязательно

Простые документы — анализ, регламент, ретроспектива, исправление опечатки —
могут создаваться сразу как финальные (без `_draft`), если в них нет
открытых вопросов для пользователя. Решение принимает ИИ по контексту;
если сомневаешься — делай `_draft`.
