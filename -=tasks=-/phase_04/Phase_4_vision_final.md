## 0. Постановка проблемы (два слоя)

### Видимое
Reverse-engineer создаёт файлы вида:
```
function sp_admin_update_order_delivery(text, varchar, varchar, varchar, uuid, uuid).sql
```
На Windows NTFS лимит имени файла — 255 символов, полного пути — 260. С учётом пути
`<output>/<db>/<schema>/functions/` такие имена могут превышать лимит и вызывать ошибки.

### Скрытое (более серьёзное)
`object_key` сейчас имеет вид `pg_database/<db>/schema/<schema>/type/function/name/<name>`
— сигнатуры в нём нет. Две перегруженные функции `sp_x(int)` и `sp_x(text)` получают
**одинаковый** `object_key`, и `DependencyGraph.add_vertex` (`graph.py:118`) молча
перезаписывает одну вершину другой. Деплой с перегрузками, скорее всего, уже некорректен —
просто этого не замечали, т.к. в `sample_structure.json` секции functions/procedures пусты.

Длинные имена — видимая часть айсберга. Чинить нужно идентификацию перегруженных функций
в целом, а не только длину имени.

---

## 1. Цель

1. **Identity-слой:** сигнатура становится частью идентичности объекта в графе и автодоке.
   Перегрузки получают разные `object_key` и не перезаписывают друг друга.
2. **Имена файлов:** короткие по умолчанию; при перегрузках — короткий SHA-256 суффикс.

---

## 2. Зафиксированные решения

| # | Решение | Обоснование |
|---|---------|-------------|
| Q1 | Суффикс имени файла — **короткий SHA-256 хеш** (8 hex-символов) | Нулевой риск коллизий для любого реального количества перегрузок; альтернативы (имена типов / гибрид) дают коллизии на коротких суффиксах или избыточно сложны |
| Q2 | Охват — **полностью** (identity-слой + file name) | Скрытый баг потери перегрузок в графе критичнее видимой проблемы длинных имён; чинить всё за один проход последовательнее |
| Q3 | Разрешение перегруженных вызовов в edge detection — **НЕ входит** в Phase 4 (Phase 5+) | Требует полноценного type inference по аргументам вызова; отдельная задача с риском регрессий |

## 3. Каноническая сигнатура

Новый модуль `src/db_project_manager/domain/signature.py`:

```python
def canonical_signature(argument_types: str) -> str:
    """'text, varchar(255), uuid' -> 'text,varchar,uuid'"""
    # lowercase, разбиение по ',', trim, удаление модификаторов (...), join ','

def signature_hash(sig: str) -> str:
    """8 hex-символов SHA-256 от canonical_signature (пустая sig -> '')"""
```

Нормализация модификаторов `(255)`, `(64,0)` обязательна: одна и та же функция в `pg_proc`
может прийти через разные текстовые представления, хеш должен быть стабилен.
`argument_types` из адаптера приходит через `pg_type.typname` — уже нормализованным,
поэтому alias-маппинг (`int4`↔`integer`) **не требуется**.

## 4. Identity-слой (граф + автодок)

### 4.1. Новое поле `Vertex.object_signature`

```python
class Vertex(BaseModel):
    # ... существующие поля ...
    object_signature: str = Field("", description="Canonical signature for overloaded functions/procedures")
```

Сериализация в `.dbm_graph/` подхватится автоматически (`graph_store` использует `model_dump`).

### 4.2. `object_key` с суффиксом сигнатуры

Для function/procedure **при непустой сигнатуре** к ключу добавляется суффикс:
```
pg_database/<db>/schema/<schema>/type/function/name/<name>/signature/<hash>
```

Для table/view/sequence и для функций без аргументов — формат `object_key` **не меняется**
(обратная совместимость со старыми `.dbm_graph/`).

### 4.3. Autodoc-заголовок

В YAML-блок автодока для function/procedure добавляется поле `object_signature`:
парсер восстанавливает его и проставляет в `Vertex`. Сам `object_key` парсер берёт
из автодока как есть (генератор уже встроил в него хеш сигнатуры при необходимости).

## 5. Имена файлов

Правило в `SQLGenerator._render_kind` для function/procedure:

1. Для каждого объекта вычисляется `base_name = f"function {name}.sql"`.
2. Объекты группируются по `name`.
3. **Если в группе один объект** → короткое имя: `function sp_y.sql`.
4. **Если в группе >1 объекта (перегрузки)** → каждому добавляется суффикс:
   `function sp_x__<signature_hash>.sql`.

### 5.1. Примеры

| БД | Файлы |
|----|-------|
| Только `sp_y(uuid)` | `function sp_y.sql` |
| `sp_x(int)`, `sp_x(text)` | `function sp_x__a1b2c3d4.sql`, `function sp_x__e5f6a7b8.sql` |
| `sp_admin_update_order_delivery(text, varchar×3, uuid×2)` (одна) | `function sp_admin_update_order_delivery.sql` |

### 5.2. Гарантия длины

Максимум ≈ **86 символов** (`"function "` + max PG identifier 63 + `"__"` + 8 hex + `".sql"`).
Гарантированно меньше 255 NTFS-лимита даже для самых длинных имён функций.

## 6. MVP-ограничение: edge detection (Q3)

`_build_names_index` (`pg_sql_parser.py:212-224`) использует голое `object_name` через
`setdefault`. При перегрузках в индексе остаётся только первая по обходу.

**Поведение в Phase 4:** вызовы функции-перегрузки в SQL создают рёбра к «первой попавшейся»
вершине. Это приемлемо для `deploy validate` — главное, что все объекты присутствуют в графе.

Разрешение перегрузок по аргументам вызова требует type inference → **вынесено в Phase 5+**.

## 8. Риски и смягчения

| Риск | Смягчение |
|------|-----------|
| `codebase_hash` инвалидируется (имена .sql-файлов изменились) | Уже предусмотрен механизм `is_stale` — граф перестроится автоматически |
| Имя файла с SHA-суффиксом всё ещё >255 символов | Невозможно: макс. ≈ 86 символов (см. §5.2) |
| Старые `.dbm_graph/` несовместимы | `object_key` для неперегруженных объектов не меняется; для перегруженных граф просто перестроится (`is_stale`) |
| Edge detection не различает перегрузки | Зафиксировано как MVP-ограничение (Q3); разрешение вызовов → Phase 5+ |
| Регрессии в существующем deploi/test контракте | Деплой берёт путь из `object_source_file` (не из имени); контракт сохраняется |

## 9. Что НЕ входит в Phase 4

  не требуется, т.к. `argument_types` из `pg_type.typname` уже приходит нормализованным.
- SSH-key auth (Phase 3 follow-up), миграции с данными (Phase 5 в roadmap).
