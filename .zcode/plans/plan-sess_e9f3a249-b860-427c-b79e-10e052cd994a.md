# Phase 4 — Идентификация перегруженных функций/процедур

## Постановка проблемы (два слоя)

**Видимое:** reverse-engineer создаёт файлы вида `function sp_admin_update_order_delivery(text, varchar, varchar, varchar, uuid, uuid).sql` — на Windows это легко превышает лимит NTFS (255 символов на имя файла, 260 на полный путь).

**Скрытое (более серьёзное):** `object_key` сейчас имеет вид `pg_database/<db>/schema/<s>/type/function/name/<name>` — **сигнатуры в нём нет**. Две перегруженные функции `sp_x(int)` и `sp_x(text)` получают одинаковый ключ, и `DependencyGraph.add_vertex` (`graph.py:118`) молча перезаписывает одну вершину другой. Деплой с перегрузками, скорее всего, уже некорректен — просто этого ещё не замечали.

**Решение, подтверждённое пользователем:**
1. Сигнатура становится частью идентичности объекта (граф + автодок).
2. Имя файла — короткое; при коллизии (перегрузки) добавляется SHA-256 суффикс.

## Каноническая сигнатура (контракт для всей фазы)

Новый модуль `src/db_project_manager/domain/signature.py`:

```python
def canonical_signature(argument_types: str) -> str:
    """'text, varchar(255), uuid' -> 'text,varchar,uuid'"""
    # lowercase, разбиение по ',', trim, удаление модификаторов (...), join ','

def signature_hash(sig: str) -> str:
    """8 hex-символов SHA-256 от canonical_signature (пустая sig -> '')"""
```

Нормализация модификаторов `(255)`, `(64,0)` обязательна: одна и та же функция в `pg_proc` может попасть к нам через разные текстовые представления, хеш должен быть стабилен.

## Шаги реализации

### P4.S01 — Доменная модель: `Vertex.object_signature` + утилиты сигнатуры
**Файлы:** `src/db_project_manager/domain/graph.py`, **новый** `src/db_project_manager/domain/signature.py`, `tests/unit/test_graph_model.py`, **новый** `tests/unit/test_signature.py`.

- Добавить поле `object_signature: str = ""` в `Vertex` (`graph.py:38-54`). Сериализация в `.dbm_graph/` подхватится автоматически (`graph_store` использует `model_dump`).
- Реализовать `canonical_signature` и `signature_hash` с тестами на:
  - `text, varchar, varchar, uuid` → стабильный хеш.
  - `varchar(255)` и `varchar` → одинаковый хеш (модификаторы игнорируются).
  - пустая строка → пустой хеш.

### P4.S02 — Autodoc: сигнатура в заголовке и `object_key`
**Файлы:** `src/db_project_manager/infrastructure/sql/autodoc.py`, `tests/unit/test_autodoc.py`.

- `build_metadata(...)` и `ensure_header(...)` принимают опциональный `object_signature`.
- `_build_object_key` для function/procedure **при непустой сигнатуре** добавляет суффикс `/signature/<hash>`:
  ```
  pg_database/db/schema/s/type/function/name/sp_x/signature/a1b2c3d4
  ```
  Для table/view/sequence и для функций без аргументов — формат `object_key` **не меняется** (обратная совместимость).
- Тесты: function с сигнатурой → ключ с `/signature/`; function без аргументов → ключ без суффикса; table → без изменений.

### P4.S03 — SQLGenerator: короткие имена файлов + SHA-суффикс при перегрузках
**Файлы:** `src/db_project_manager/infrastructure/sql/sql_generator.py`, `tests/unit/test_sql_generator.py`, `tests/fixtures/sample_structure.json`.

- `_function_ctx`/`_procedure_ctx` вычисляют `signature = canonical_signature(argument_types)` и кладут её в контекст + возвращают как третье значение тапла. Имя файла из ctx_builder убирается — его соберёт `_render_kind`.
- `_render_kind` (`sql_generator.py:189-207`) для function/procedure:
  1. Собирает все `base_name = f"function {name}.sql"` для группы.
  2. Группирует по `name`. Если в группе >1 элемента (перегрузка) → каждому добавляется `__<signature_hash>`: `function sp_x__a1b2c3d4.sql`.
  3. Если элемент один → короткое имя `function sp_x.sql`.
- Передача `object_signature` в `_render_one` → `ensure_header` (чтобы автодок содержал хеш).
- Расширить `sample_structure.json`: schema `app` с двумя перегруженными функциями `sp_x(int)` / `sp_x(text)` и одиночной `sp_y(uuid)`.
- Тесты:
  - Одиночная функция → файл `function sp_y.sql`.
  - Перегрузки → `function sp_x__<hash1>.sql`, `function sp_x__<hash2>.sql`, хеши различаются.
  - В автодок-заголовке файлов перегрузок — `/signature/<hash>`.

### P4.S04 — PgSqlParser: восстановление сигнатуры из автодока
**Файлы:** `src/db_project_manager/infrastructure/parsing/pg_sql_parser.py`, `tests/unit/test_pg_sql_parser.py`, `tests/fixtures/codebase_sample/`.

- В ветке с автодоком (`_parse_file`, `pg_sql_parser.py:147-167`): читать `object_signature` из `obj_meta` и проставлять в `Vertex`. Сам `object_key` берётся из автодока как есть (он уже содержит сигнатуру, если S02 отработал).
- Расширить `codebase_sample/` — добавить `app/functions/function sp_x__a1b2c3d4.sql` и `function sp_x__e5f6a7b8.sql` с автодок-заголовками.
- Тесты:
  - Два файла перегрузок → две разные вершины с разными `object_key`.
  - `object_source_file` проставлен корректно (относительный posix-путь).
  - Граф после `filter_build_true` содержит обе вершины.

### P4.S05 — Edge detection: зафиксировать MVP-ограничение
**Файлы:** `-=tasks=-/phase_04/Phase_4_vision_final.md` (только документация).

`_build_names_index` (`pg_sql_parser.py:212-224`) использует голое `object_name` через `setdefault` — при перегрузках в индексе остаётся только одна. Разрешение, **какая именно** перегрузка вызывается, требует type inference по аргументам вызова — это не входит в Phase 4. Фиксируем в vision как known limitation → Phase 5+.

Код в `_build_names_index` **не меняем** — это была бы отдельная задача с риском регрессий на текущих тестах.

## Риски и смягчения

| Риск | Смягчение |
|------|-----------|
| `codebase_hash` инвалидируется (имена .sql-файлов изменились) | Уже предусмотрен механизм `is_stale` — граф перестроится автоматически |
| Имя файла с SHA-суффиксом всё ещё >255 символов | Невозможно: "function " (9) + max PG identifier (63) + "__" (2) + 8 hex + ".sql" (4) ≈ 86 символов |
| Старые `.dbm_graph/` incompatible | `object_key` для неперегруженных объектов не меняется; для перегруженных граф просто перестроится (есть `is_stale`) |
| Edge detection не различает перегрузки | Зафиксировано как MVP-ограничение в vision; разрешение вызовов → Phase 5+ |
| Регрессии в существующем deploi/test контракте | Деплой берёт путь из `object_source_file` (не из имени); тесты на это есть |

## Что НЕ входит в Phase 4

- Разрешение перегруженных вызовов в edge detection (type inference по аргументам).
- Нормализация алиасов типов (`character varying` ↔ `varchar` ↔ `int4` ↔ `integer`) — `argument_types` из `pg_type.typname` уже приходит в нормализованном виде, поэтому alias-маппинг не нужен.
- SSH-key auth, миграции с данными (Phase 3/5 по roadmap).
