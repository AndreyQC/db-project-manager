# Lessons Learned — Phase 1

Практические уроки, извлечённые в ходе реализации и ручного тестирования Phase 1.
Каждый пункт — реальная находка из прогонов против живой БД, не абстрактный совет.

## Инфраструктура / окружение

### 1. uv и корпоративный TLS-прокси (Kaspersky)
- **Симптом:** `uv sync` падает с `invalid peer certificate: UnknownIssuer`, хотя `pip` работает.
- **Причина:** uv/rustls игнорирует `SSL_CERT_FILE`/`REQUESTS_CA_BUNDLE`/`CURL_CA_BUNDLE` (это переменные для OpenSSL-стека, который использует pip). uv доверяет только системному хранилищу сертификатов.
- **Решение:** перед каждым вызовом `uv` снимать эти переменные:
  ```bash
  unset SSL_CERT_FILE REQUESTS_CA_BUNDLE CURL_CA_BUNDLE && uv sync
  ```
- **Урок:** uv и pip используют разные TLS-стеки; переменные окружения, работающие для pip, бесполезны для uv. Документируй это в `PREPAREENV.md`, чтобы коллеги не споткнулись.

### 2. Установка сертификатов в систему — последний resort
- Корпоративный сертификат можно импортировать в `CurrentUser\Root`, и тогда `uv --native-tls` заработает без снятия переменных. Но это модификация системного хранилища — делай только если `unset` неудобен, и не в автоматизации/CI.

## Перенос кода из POC

### 3. Опечатки при ручном переносе SQL — главный источник runtime-багов
- **Симптом:** `psycopg2.errors.UndefinedColumn: столбец owning_col.atttypod не существует` при `get_sequences`.
- **Причина:** при переносе 1080-строчного `database.py` в `queries.py` столбец `owning_col.atttypmod` превратился в `atttypod` (переставлены `m`/`o`). В оригинале было правильно.
- **Решение:** добавлен `tests/unit/test_queries.py`, который сканирует все `<alias>.<attr>` ссылки в запросах и падает, если встречает столбец не из валидного множества `pg_attribute`.
- **Урок:** при переносе SQL-текстов из монолитного файла в структурированные константы — обязательно статическая проверка имён столбцов (тестом или сравнением с источником). PostgreSQL подсказывает правильное имя в HINT, но это runtime — лучше ловить в CI.

### 4. «Дьявол в деталях» старого god-class
- При переносе `PGDatabaseModel` (1080 строк) оптимизировал `_build_table` через хитрое list comprehension с двойным `for` — получилось нечитаемо и почти багом. Переписал простым циклом.
- **Урок:** при переносе не пытайся «улучшить» в той же правке — сначала точный перенос, потом рефакторинг отдельным коммитом. Иначе смешиваешь баги переноса с багами рефакторинга.

## Шаблоны Jinja2

### 5. trim_blocks/lstrip_blocks ломают строки, оканчивающиеся блочным тегом
- **Симптом:** колонки таблицы склеивались в одну строку: `a int NOT NULL, -- c1    b text NOT NULL`.
- **Причина:** `trim_blocks=True` срезает `\n` после блочного тега. Контент-строка оканчивалась на `{% endif %}` → её trailing-перенос срезался → строки сливались.
- **Решение:** вынес inline-логику (`{% if %}...{% endif %}` в конце строки) в helper-функции (`_type_mod`, `_null_mod`, `_comment_mod`), зарегистрированные в `env.globals`. Теперь каждая строка шаблона оканчивается на plain text, а не на тег.
- **Урок:** `trim_blocks`/`lstrip_blocks` удобны, но строка контента не должна заканчиваться блочным тегом — иначе теряется перенос. Проверяй рендер визуально на фикстуре, не только assert'ами.

### 6. Баги POC, которые всплыли при переносе шаблонов
- `table.sql.j2`: в секции FK использовалось `{{ c.comment }}` при итерации `f` → undefined.
- `col.default != 'None'` (строковое сравнение с Python-`None`) → всегда True → `DEFAULT None` в выводе.
- `numeric_scale=0` — falsy, поэтому проверка `{% if numeric_precision and numeric_scale %}` теряла точность для `int4(32, 0)`.
- **Урок:** перенос = хороший момент найти и исправить баги оригинала. Покрывай шаблоны тестами на фейковой структуре (`tests/fixtures/sample_structure.json`), которые проверяют конкретные подстроки вывода.

## Безопасность / crypto

### 7. «Не работает шифрование» чаще всего — не шифрование
- **Симптом:** `password authentication failed for user "postges"`.
- **Гипотеза (ошибочная):** пароль не расшифровывается.
- **Реальность:** расшифровка работала корректно (`token → 'Yebvjhlf#21'`); пользователь был с опечаткой `postges` вместо `postgres`.
- **Урок:** при `auth failed` сначала проверяй **значения** полей (username/password), а не механизм crypto. Добавь кнопку-«глаз» в UI для показа пароля — такие опечатки видны сразу. Диагностируй через `ConnectionStore.load(path)` в REPL: `cfg.password`, `cfg.username`.

### 8. Молчаливое глотание ошибок в `get_decrypted_nested_dict`
- В переносимом `crypto_util` строка, которую не удалось расшифровать, возвращается как есть (с warning). Это правильно для устойчивости, но **маскирует** реальную проблему: если env-ключ не задан, паролем становится сам токен → `auth failed`.
- **Урок:** при отладке crypto проверяй, что `password` не начинается с `crypto__` после load — если начинается, расшифровка не состоялась.

## CLI / Typer

### 9. Typer сворачивает единственную команду в root
- **Симптом:** `db-pm reverse-engineer ...` → `Got unexpected extra argument (reverse-engineer)`.
- **Причина:** typer с одним `@app.command()` делает его root-командой без имени; имя подкоманды игнорируется.
- **Решение:** добавлен пустой `@app.callback()`, и `db-pm` стал мультикомандной группой — `reverse-engineer` теперь подкоманда.
- **Урок:** даже для одной команды сразу делай typer-приложение мультикомандным (через callback или вторую команду). Это стоит копейки, зато команда звётся по имени и легко расширяется (`build`, `deploy`, `diff`).

## GUI / PySide6

### 10. QScintilla для PySide6 — почти тупик
- `pyside6-scintilla` (5.6.3.6) — заброшенный прототип 2023, конфликтует с PySide6 6.8.3 (тянет 6.11).
- `bscintillaedit` (преемник) — нет wheel, только sdist, требует сборку C++ через CMake (на машине без MSVC не ставится).
- **Решение Phase 1:** `QPlainTextEdit` + `QSyntaxHighlighter` (встроено в PySide6, ноль зависимостей, 96 SQL-ключевых слов). Scintilla отложен в Phase 2.
- **Урок:** сторонние bindings к Qt-виджетам часто публикуются только sdist — проверяй наличие wheel **до** того, как заложить пакет в архитектуру. Встроенных виджетов (`QSyntaxHighlighter`) обычно хватает для read-only preview.

### 11. Блокировка UI при «Тесте соединения»
- Кнопка «Тест» вызывает `adapter.connect()` синхронно в UI-потоке → при зависшем/долгом коннекте UI «замерзает», а Ctrl+C даёт `KeyboardInterrupt` внутри `rowCount` модели (это артефакт, не баг модели).
- Reverse-engineer вынесен в `QRunnable` и не блокирует; «Тест» остался синхронным.
- **Урок:** любое действие, идущее в сеть/БД, — кандидат на фоновый поток. Либо выноси тест-кнопку в `QRunnable`, либо показывай пользователю, что процесс идёт (busy-cursor + таймаут).

### 12. `git add` для каталога, начинающегося с `-`
- `mkdir -=tasks=-` и `git add -=tasks=-/...` ломают парсинг опций (bash/git принимают за флаг).
- **Решение:** `mkdir -p -- "-=tasks=-"` и `git add -- "-=tasks=-/..."` (двойной дефис отделяет опции от путей).
- Также `connections/*` + `!connections/example.yaml` — negation файла внутри игнорируемой **директории** не работает в git (нужно игнорировать содержимое `connections/*`, а не сам каталог).

## Процесс / дисциплина

### 13. Flaky-тесты на env-фикстуры
- `test_save_load_roundtrip` изредка падал в полном прогоне, изолированно — зелёный.
- **Причина:** пересечение `monkeypatch.setenv(TEST_CRYPTO_ENV, ...)` между `test_crypto_util` и `test_connection_store` при определённом порядке/тайминге.
- **Урок:** env-зависимые тесты должны быть полностью изолированы (свой ключ, своя переменная, явная очистка). Если тест флапает — это не «косвенность», а реальное загрязнение состояния; разбирайся, не игнорируй.

### 14. Документируй нестандартные требования окружения
- Все находки выше (TLS-прокси, env crypto-ключ, сборка C++) в итоге легли в `PREPAREENV.md` и `README.md`. Коллега, который впервые клонирует репо, должен иметь рабочий setup без телепатии.
- **Урок:** любая нестандартность окружения, на которую ты потратил >5 минут — это материал для `PREPAREENV.md`. Не оставляй решение только в истории bash.

## Phase 2 — дополнительные уроки

### 15. Недостижимые `elif` в парсере — тихий баг
- **Симптом:** `left join` классифицировался как `inner join`; специфичные `right join`/`full outer join` вообще не обрабатывались.
- **Причина:** в POC-парсере общий `elif words[i-1] == "join"` стоял **раньше** специфичных (`left join`, `full outer join`), поглощая все варианты. Python вычисляет elif по порядку — общий всегда срабатывал первым.
- **Решение:** специфичные проверки (`left join`, `right join`, `full outer join`, `inner join`) — **до** общего `join`. Регрессионный тест: fixture с реальным `LEFT JOIN` + assert на `action == "select left join"`.
- **Урок:** при переносе каскадов `if/elif` рисуй их на бумаге и проверяй порядок специфичности. Токен перед/после — хрупкая эвристика, требующая тестов на каждый вариант.

### 16. Дедупликация через `set(tuple(sorted(d.items())))` — ломается на смешанных типах
- **Причина:** POC дедуплицировал рёбра, сортируя items dict'а. Когда значения смешанных типов (`None`, `str`), сравнение падает или даёт неверный результат.
- **Решение:** `Edge.dedup_key()` возвращает хешируемый tuple фиксированной формы `(source, destination, relation, action)`. Явный контракт вместо неявной сортировки.
- **Урок:** для дедупликации объектов с известной идентичностью — всегда явный `dedup_key()`, не «отсортируем items».

### 17. Отключённая проверка циклов в топосортировке = тихая потеря объектов
- **Симптом:** граф с циклом разворачивался бы без ошибок, но часть объектов исчезала из deploy-порядка.
- **Причина:** в POC проверка `len(result) != len(vertices)` была **закомментирована** «потому что циклы есть и это норма» — но без различения «намеренно проигнорировали» vs «упустили баг».
- **Решение:** возвращена явная `CycleError(unresolved=[...])` со списком проблемных вершин. Команда `db-pm graph validate` сообщает цикл по имени, а не молча.
- **Урок:** закомментированная проверка — это долг. Либо восстанови с явным обоснованием «почему игнорируем», либо удали. Молчаливая потеря данных в deploy-инструменте — критично.

### 18. Контракт адаптера — расширяй с regression-тестом на моках
- При добавлении 5 методов в `DatabaseAdapter` (Phase 2: createdb/timestamp/execute/drop) сразу сломался `FakeAdapter` в тестах reverse-engineer — `Can't instantiate abstract class`.
- **Решение:** ABC + интеграционный FakeAdapter в тестах, который реализует весь контракт (даже неиспользуемые в данном сценарии методы — как no-op/stub).
- **Урок:** при расширении ABC сначала прогони существующие тести — они подсветят всех потребителей. Держи общий FakeAdapter в conftest, не дублируй в каждом тесте.

### 19. SQL-инъекция в `CREATE DATABASE` — whitelist имён
- POC собирал `CREATE DATABASE` через f-string из пути пользователя — классическая инъекция. Phase 1 analysis это отметил, Phase 2 реализовала через `_validate_db_name` whitelist `[A-Za-z_][A-Za-z0-9_]*` + double-quoted identifier.
- **Урок:** любой DDL с идентификатором из пользовательского ввода — whitelist + escaping. 14 параметризованных тестов покрывают валидные и инъекционные кейсы (`'has; DROP TABLE x; --'`).

### 20. OS-зависимые пути ломают воспроизводимость графа
- **Симптом:** на Windows `path.relative_to(root)` давал `bookings\tables\...`, на Linux — `bookings/tables/...`. Хэш кодовой базы и `.dbm_graph/` отличались между ОС для одного контента.
- **Решение:** `_relative_posix(path, root)` всегда возвращает forward-slash; `codebase_hash` хеширует posix-пути. Граф идентичен на любой ОС.
- **Урок:** всё, что сериализуется или хешируется и может оказаться в CI на другой ОС — нормализуй к forward-slash (`.as_posix()` в pathlib).

### 21. Python Docker SDK на Windows не видит daemon
- **Симптом:** `docker.errors.DockerException: CreateFile ... The system cannot find the file specified.` при `docker.from_env()` в testcontainers.
- **Причина:** Python SDK использует named pipe `//./pipe/docker_engine` (default context), а активный контекст Docker Desktop — `npipe:////./pipe/dockerDesktopLinuxEngine`. Но корневая причина оказалась проще: **Docker Desktop daemon не был запущен** (CLI `docker version` показывал только Client).
- **Решение:** integration-тесты маркированы `@pytest.mark.integration` и **deselected по умолчанию** (`addopts = "-m 'not integration'"`), чтобы unit-прогон не зависел от Docker. Запуск integration — отдельная команда `uv run pytest -m integration`, требующая запущенного Docker.
- **Урок:** когда тест требует внешнего сервиса (Docker, БД, сеть) — маркируй и исключай из дефолтного прогона. Не смешивай «быстрые детерминированные unit» с «медленным окружением».

### 22. Flaky env-тесты (продолжение §13)
- `test_save_load_roundtrip` и `test_encrypt_decrypt_roundtrip` периодически падали в полном прогоне, изолированно — зелёные.
- **Причина:** пересечение `monkeypatch.setenv(TEST_CRYPTO_ENV, ...)` между `test_crypto_util` и `test_connection_store` при определённом порядке/тайминге. Фикстура `crypto_env` через `monkeypatch` теоретически чистая, ноTiming в Windows иногда даёт гонки.
- **Урок (повтор §13):** env-зависимые тесты — полностью изолируй (свой ключ, своя переменная, явная teardown). Если тест флапает — не отмахивайся, разбирай причину; для CI flaky = недоверие к тестам.

### 23. Autodoc-заголовок удобен для парсера, но должен стрипься перед execute
- Файл содержит SQL + autodoc YAML-блок. Парсер читает метаданные из блока (источник правды), а деплой-сервис **обязан стрипнуть** блок перед `execute_script`, иначе `/*...*/` комментарий уйдёт в БД (безвредно, но лишний шум и медленнее).
- **Урок:** формат «данные + код в одном файле» требует чёткого разделения по потребителю: парсер — данные, исполнитель — код. Стрипай метаданные перед передачей исполнителю.

## Phase 3 — SSH Tunnel

### 24. SSH port forwarding с paramiko требует full-duplex пиринга
- **Симптом:** Туннель поднимается успешно ("SSH tunnel ready on port N"), но PG-клиент зависает после отправки startup-пакета. Данные уходят в канал (8 байт), ответ не приходит.
- **Корневая причина:** `_pipe` передавал данные только в одну сторону (`client.recv → channel.sendall`). Ответ PG-сервера (channel → client) никто не читал и не писал обратно в `client_sock`. PG-клиент отправлял startup-пакет и ждал ответа, ответ базы зависал в буфере канала.
- **Исправление:** Два отдельных потока для full-duplex:
  - `_pipe_client_to_channel`: читает из PG-сокета, пишет в SSH-канал
  - `_pipe_channel_to_client`: читает из SSH-канала, пишет в PG-сокет
- **Урок:** При реализации port forwarding через SSH-канал — данные текут **в обе стороны**. Один поток с блокирующим `channel.recv()` не подходит. Нужен либо два потока (как в данном решении), либо `select`/`asyncio` для асинхронного мультиплексирования.

### 25. paramiko 5.x несовместим с `sshtunnel`
- **Симптом:** При попытке использовать `sshtunnel.SSHTunnelForwarder` — конфликт версий или ошибки импорта.
- **Причина:** `sshtunnel` использует внутренние API paramiko, которые изменились в 5.x.
- **Решение:** Реализован собственный `SSHTunnelManager` на чистом paramiko с `transport.open_channel("direct-tcpip", ...)`.
- **Урок:** При выборе библиотеки-обёртки (sshtunnel) проверяй совместимость с latest версией зависимости. Альтернатива — реализовать на low-level API напрямую, если обёртка не поддерживается.

## Phase 4 — Идентификация перегруженных функций/процедур

### 26. `object_key` без сигнатуры = silent overwrite перегрузок
- **Симптом:** Две перегруженные функции `sp_x(int)` и `sp_x(text)` при `graph build`
  превращались в **одну** вершину — вторая молча перезаписывала первую в
  `DependencyGraph.add_vertex` (`graph.py:118`).
- **Корневая причина:** `object_key` имел вид `pg_database/<db>/schema/<s>/type/function/name/<name>`
  — **сигнатуры в ключе не было**. Для перегрузок ключ совпадал, и в `dict[str, Vertex]`
  оставался только последний вставленный. Деплой с перегрузками, скорее всего, уже был
  некорректен — просто этого не замечали, т.к. в `sample_structure.json` секции
  functions/procedures были пусты.
- **Видимая часть проблемы:** длинные имена файлов
  (`function sp_x(text, varchar, varchar, varchar, uuid, uuid).sql`) превышали лимит NTFS
  (255 символов). Это был лишь симптом; корень — в идентификации, а не в именах.
- **Исправление (Phase 4):**
  - `Vertex.object_signature` (8 hex SHA-256 от canonical signature).
  - `object_key` для function/procedure при непустой сигнатуре получает суффикс
    `/signature/<hash>` — детерминированно, независимо от наличия соседей-перегрузок.
  - Имя файла управляется отдельной логикой: короткое по умолчанию, `__<hash>` суффикс
    только при реальной коллизии (чтобы имена оставались читаемыми).
- **Урок:** «длинное имя файла» часто — лишь верхушка айсберга; проверяй, как тот же
  идентификатор используется в графе/хранилище/деплое. Если в ключе идентичности нет
  сигнатуры — перегрузки теряются молча. Любое «сокращение» в отображаемом имени должно
  сохранять однозначное отображение в канонический идентификатор.

### 27. Каноническая сигнатура: выкидывать модификаторы ДО split, а не после
- **Симптом:** `canonical_signature("numeric(10,2)")` возвращала `"numeric(10,2)"`
  вместо `"numeric"` — хеш отличался от `signature_hash("numeric")`.
- **Причина:** исходный regex `_MOD_RE` применялся к **каждой части** после `split(",")`,
  но `numeric(10,2)` сплитовалась в `["numeric(10", "2)"]` — ни одна часть не содержит
  полной скобки. Хеш одного и того же объекта зависел от того, как его текстовое
  представление разбилось на части.
- **Исправление:** `_MOD_RE` применяется к **всей строке** до `split`, тогда вложенные
  запятые внутри `(10,2)` вырезаются целиком. Regex: `r"\s*\([^)]*\)"` (не anchored).
- **Урок:** при нормализации сложных идентификаторов сначала — глобальные
  преобразования (вырезание скобок/кавычек), потом — токенизация. Порядок «split → transform»
  хрупок, если separator может встретиться внутри transform-блока. Покрывай тестами
  типы с модификаторами-с-запятыми (`numeric(10,2)` — классика).

### 28. PyYAML «кавычит» чисто-числовые строки — не точный substring в тестах
- **Симптом:** `assert "object_signature: 75666699" in text` падало, хотя в файле
  было `object_signature: '75666699'`.
- **Причина:** 8-hex подпись может оказаться 8-значным числом (`75666699`), и PyYAML
  добавляет одинарные кавычки, иначе значение парсилось бы как int.
- **Исправление:** в тестах используем `assert hash in text` (или парсим через
  `extract_header`), а не точный substring.
- **Урок:** при тестировании YAML-сериализации предпочитай roundtrip через парсер
  (`extract_header(decorated)["object"]["object_signature"]`), а не substring-матчинг
  по сырой строке. Roundtrip устойчив к стилям кавычек/отступов YAML.

## Phase 5 — PostgreSQL extensions и настройки базы

### 29. Schema-less объекты проходят через весь конвейер без изменений
- **Симптом:** `extension` и `database_setting` не привязаны к схеме; на всём пути
  `object_schema=None` → `schema/` сегмент опускается в `object_key`, `_render_one`
  получает `object_schema=None`, autodoc пишет ключ без `schema/`, парсер создаёт
  вершину с `object_schema=None`.
- **Решение:** ни одного хака не потребовалось — существующий код уже поддерживал
  nullable `object_schema`. Добавили `extension`/`database_setting` в
  `SUPPORTED_TYPES`, `_CREATE_KEYWORD_TO_TYPE`, `TYPE_PRIORITIES`, `EARLY_DDL_TYPES`.
- **Урок:** новые типы объектов, не привязанные к схеме, можно добавлять по
  образцу существующих, если сразу проверять все слои конвейера (queries →
  structure → generator → autodoc → parser → toposort → deploy).

### 30. Pydantic v2 отвергает `extra=None` — не передавай поле при пустом словаре
- **Симптом:** `Vertex(..., extra=None)` падало с `Input should be a valid
  dictionary [type=dict_type, input_value=None, input_type=NoneType]` на всех
  файлах без `extra`.
- **Причина:** Pydantic v2 не разрешает `None` для `dict`-поля; предыдущая версия
  пропускала.
- **Решение:** `**({"extra": extra} if extra else {})` — не передавать `extra`
  вовсе, когда словарь пустой.
- **Урок:** при добавлении новых необязательных полей в модели с Pydantic-валидацией
  всегда проверяй, что `None` корректно обрабатывается (или не используется).

### 31. Windows `tmp_path` не создаёт промежуточные директории через `Path.write_text`
- **Симптом:** `(tmp_path / ".dbm_graph" / "ext.sql").write_text(...)` падало с
  `FileNotFoundError` на Windows при использовании pytest `tmp_path`.
- **Причина:** `Path.write_text` вызывает `os.open` с флагами `O_CREAT|O_WRONLY|O_TRUNC`
  без `O_DIRECTORY` — если промежуточная директория не существует, она не
  создаётся (в отличие от Linux/macOS где `Path.mkdir` часто делается неявно или
  файловая система по-другому обрабатывает флаг).
- **Решение:** явно `dbm.mkdir()` перед записью вложенного файла.
- **Урок:** при работе с `tmp_path` в кросс-платформенном коде всегда создавай
  промежуточные директории явно (`mkdir -p` equivalent), а не полагайся на то,
  что они уже существуют.

### 32. LC_COLLATE/LC_CTYPE требуют одинарных кавычек и реальной локали на сервере
- **Симптом:** `CREATE DATABASE ... LC_COLLATE C.UTF-8` падало с `SyntaxError`
  (точка воспринималась как оператор), а затем с `WrongObjectType: invalid locale name`.
- **Причина #1:** значения locale содержат точки/пробелы (`C.UTF-8`) и должны быть
  в **одинарных** кавычках в SQL, не как bare identifier.
- **Причина #2:** локаль `C.UTF-8` может не существовать на целевом сервере —
  кластерная локаль определяется при инициализации и не включает все возможные варианты.
- **Решение:** (1) значения locale оборачиваются в `'...'`; (2) при ошибке
  `WrongObjectType` делается fallback `CREATE DATABASE ... TEMPLATE template0`
  — стандартная практика PostgreSQL, когда locale не совпадает.
- **Урок:** при переносе `CREATE DATABASE` свойств всегда предусматривай fallback
  на `template0`; без него validate ломается на любом сервере с отличным набором
  локалей. Документируй это ограничение в PREPAREENV.md если инструмент будет
  использоваться в environments с нестандартными локалями.

### 33. Sequence nextval lookup требует схемы источника, а не bare name
- **Симптом:** `audit_log` (схема `qr`) падала с `UndefinedTable: relation
  "audit_log_id_seq" does not exist` при deploy — последовательность в схеме `qr`,
  но `nextval('audit_log_id_seq')` без схемы.
- **Корневая причина:** `_scan_edges` делал lookup токена `audit_log_id_seq` по
  `names_index` — искал `audit_log_id_seq` и находил вершину, но topological sort
  между таблицей и последовательностью в разных схемах (или с несогласованным
  схемным префиксом в `nextval`) не создавал рёбер. Плюс disconnected vertices
  сортировались по alpha, а не по type priority.
- **Фикс (двойной):**
  1. `_scan_edges`: при `SEQUENCE_NEXTVAL_IN`优先 использовать схему таблицы-
    источника для lookup: `qr.audit_log_id_seq` → последовательность в схеме `qr`.
  2. `sort_by_type_and_topology`: disconnected vertices (in-degree=0, out-degree=0)
    получают topo_index += 1000, чтобы type priority доминировала (sequence=1
    до table=2 даже без explicit edge).
- **Урок:** идентификаторы в SQL без схемы (bare `nextval('seq')`) должны
  резолвиться через контекст схемы **текущего объекта**, а не через глобальный
  поиск. Всегда проверяй cross-schema сценарии.

### 34. Reverse-engineer обязан выдавать fully-qualified имена в DEFAULT
- **Симптом:** deploy validate падал с `UndefinedTable: relation "audit_log_id_seq"
  does not exist` — последовательность в схеме `qr`, а `nextval('audit_log_id_seq')`
  в DEFAULT таблицы `qr.audit_log` без схемы.
- **Корневая причина:** `information_schema.columns.column_default` содержит
  ровно то, что задал разработчик при `CREATE TABLE` — **без схемы**, если не указано.
  Reverse-engineer вытягивал значение как есть, и при deploy на временной БД
  с другим `search_path` PostgreSQL не находил последовательность.
- **Фикс на корне:** при reverse-engineer в `_build_table` helper
  `_qualify_default_schema(default, schema)` подставляет схему таблицы в bare
  sequence refs в `nextval(...)`/`currval(...)`. Уже-qualified имена остаются
  как есть. Несeq defaults (`now()`, литералы) не трогаются.
- **Урок:** любой инструмент, генерирующий DDL из каталога, должен **нормализовать
  идентификаторы к fully-qualified виду** на этапе reverse-engineer, а не
  рассчитывать, что `search_path` на целевой БД совпадёт с исходной. Bare имена —
  мина, которая взрывается на любой БД с отличным `search_path` (включая
  временную БД из `template0`, где `search_path` дефолтный).
