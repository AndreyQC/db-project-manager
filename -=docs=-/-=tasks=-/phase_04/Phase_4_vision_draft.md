## 0. Почему это важно

### Видимая проблема
При reverse-engineering БД с функциями/процедурами, у которых много параметров, имя файла получается очень длинным:

```
function sp_admin_update_order_delivery(text, varchar, varchar, varchar, uuid, uuid).sql
```

На Windows NTFS лимит имени файла — 255 символов, полного пути — 260 символов. С учётом
пути `<output>/<db>/<schema>/functions/` такие имена могут превышать лимит и вызывать
ошибки записи/чтения.

### Скрытая проблема (более серьёзная)
Текущий `object_key` имеет вид:
```
pg_database/<db>/schema/<schema>/type/function/name/<name>
```

**Сигнатуры в ключе нет.** Две перегруженные функции `sp_x(int)` и `sp_x(text)` получают
**одинаковый** `object_key`. В `DependencyGraph.add_vertex` (`graph.py:118`) вторая
вершина молча перезаписывает первую. Деплой с перегрузками, скорее всего, уже некорректен —
просто этого ещё не замечали, т.к. в тестах `sample_structure.json` секции functions/procedures
**пусты**.

Длинные имена файлов — видимая часть айсберга. Чинить нужно идентификацию перегруженных
функций в целом, а не только длину имени.

---

## 1. Цель Phase 4

1. **Identity-слой:** сигнатура становится частью идентичности объекта в графе и автодоке.
   Перегрузки получают разные `object_key` и не перезаписывают друг друга.
2. **Имена файлов:** короткие по умолчанию (`function sp_x.sql`); при перегрузках —
   добавляется короткий SHA-256 суффикс (`function sp_x__a1b2c3d4.sql`).

**Критерий «фаза готова»:**
- `reverse-engineer` на БД с перегруженными функциями создаёт файлы с уникальными короткими именами.
- `graph build` помещает каждую перегрузку в отдельную вершину с уникальным `object_key`.
- `db-pm deploy` корректно деплоит все перегрузки.
- Существующий контракт (table/view/sequence, функции без аргументов) не меняется.

## 2. Каноническая сигнатура

Новый модуль `src/db_project_manager/domain/signature.py`:

```python
def canonical_signature(argument_types: str) -> str:
    """'text, varchar(255), uuid' -> 'text,varchar,uuid'"""
    # lowercase, разбиение по ',', trim, удаление модификаторов (...), join ','

def signature_hash(sig: str) -> str:
    """8 hex-символов SHA-256 от canonical_signature (пустая sig -> '')"""
```

**Зачем нормализация модификаторов:**
одна и та же функция в `pg_proc` может прийти через разные текстовые представления
(`varchar(255)` vs `varchar`). Хеш должен быть стабилен при логически одинаковой сигнатуре.
Поле `argument_types` в адаптере (`adapter.py:414`) приходит из `pg_type.typname` —
уже в нормализованном виде, поэтому alias-маппинг (`int4`↔`integer`) **не нужен**.

## 3. Identity-слой (граф + автодок)

### 3.1. Новое поле `Vertex.object_signature`

```python
class Vertex(BaseModel):
    # ... существующие поля ...
    object_signature: str = Field("", description="Canonical signature for overloaded functions/procedures")
```

Сериализация в `.dbm_graph/` подхватится автоматически (`graph_store` использует `model_dump`).

### 3.2. `object_key` с суффиксом сигнатуры

Для function/procedure **при непустой сигнатуре** к ключу добавляется суффикс:
```
pg_database/<db>/schema/<schema>/type/function/name/<name>/signature/<hash>
```

Для table/view/sequence и для функций без аргументов — формат `object_key` **не меняется**
(обратная совместимость со старыми `.dbm_graph/`).

### 3.3. Autodoc-заголовок

В YAML-блок автодока для function/procedure добавляется поле `object_signature`:
парсер восстанавливает его и проставляет в `Vertex`. Сам `object_key` парсер берёт
из автодока как есть (генератор уже встроил в него хеш сигнатуры при необходимости).

## 4. Имена файлов

Правило в `SQLGenerator._render_kind` для function/procedure:

1. Для каждого объекта вычисляется `base_name = f"function {name}.sql"`.
2. Объекты группируются по `name`.
3. **Если в группе один объект** → короткое имя: `function sp_y.sql`.
4. **Если в группе >1 объекта (перегрузки)** → каждому добавляется суффикс:
   `function sp_x__<signature_hash>.sql`.

### 4.1. Примеры

| БД | Файлы |
|----|-------|
| Только `sp_y(uuid)` | `function sp_y.sql` |
| `sp_x(int)`, `sp_x(text)` | `function sp_x__a1b2c3d4.sql`, `function sp_x__e5f6a7b8.sql` |
| `sp_admin_update_order_delivery(text, varchar×3, uuid×2)` (одна) | `function sp_admin_update_order_delivery.sql` |

### 4.2. Гарантия длины

Максимальная длина имени файла:
- `"function "` — 9 символов
- max PG identifier (63) — 63 символа
- `"__"` — 2 символа
- 8 hex-символов SHA-256 — 8 символов
- `".sql"` — 4 символа

Итого ≈ **86 символов** — гарантированно меньше 255 даже для самых длинных имён
функций в PostgreSQL.

### Q1. Формат суффикса для перегруженных функций/процедур в имени файла

Варианты:
- **(a) Короткий SHA-256 хеш** (8 hex-символов): `sp_x__a1b2c3d4.sql`.
  Технологически чисто, нулевой риск коллизий. Минус: по имени файла не виден набор типов.
- **(b) Короткие имена типов**: `sp_x__int4_text.sql`.
  Читаемый. Минусы: коллизии (`integer` vs `int4` оба `i`), хрупкость на типах с параметрами,
  при многих параметрах имя снова длиннеет.
- **(c) Гибрид**: сначала имена типов, при коллизии — хеш.
  Максимальная читаемость + гарантия отсутствия коллизий, но самый сложный в реализации.

```
USER_INPUT:
(a) Короткий SHA-256 хеш (8 hex-символов).
Обоснование: нулевой риск коллизий для любого реального количества перегрузок,
технологически чистое решение. Вариант (b) даёт коллизии на коротких суффиксах
(i для integer/int4/int8), а гибрид (c) избыточно сложен ради сомнительной выгоды.
```

### Q2. Охват фазы — чинить ли фундаментальную проблему с `object_key`

Текущая архитектура теряет сигнатуру в графе: две перегрузки получают одинаковый
`object_key`, и `DependencyGraph.add_vertex` молча перезаписывает одну другой.
Деплой с перегрузками, скорее всего, уже некорректен.

Варианты:
- **(a) Полностью:** identity-слой (signature в Vertex + object_key) И file name.
  Фиксит и длинные имена, и скрытый баг с потерей перегрузок в графе.
- **(b) Только имена файлов:** `object_key` пока не трогать, задел на отдельную фазу.

```
USER_INPUT:
(a) Полностью.
Обоснование: длинные имена файлов — видимая часть проблемы; скрытая (потеря перегрузок
в графе) критичнее для корректности деплоя. Чинить всё за один проход последовательнее,
чем оставлять фундаментальный баг «на потом».
```

### Q3. (уточнение) Разрешение перегруженных вызовов в edge detection

`_build_names_index` (`pg_sql_parser.py:212-224`) использует голое `object_name` через
`setdefault` — при перегрузках в индексе остаётся только одна (первая по обходу).
Разрешение, **какая именно** перегрузка вызывается, требует type inference по аргументам
вызова функции.

Должно ли это входить в Phase 4?

```
USER_INPUT:
Нет — вынести в Phase 5+.
Обоснование: разрешение перегрузок по аргументам вызова — это полноценный type inference,
отдельная задача с риском регрессий. В Phase 4 фиксируем идентификацию (разные object_key
для перегрузок), а edge detection оставляем как есть (MVP: индекс по голому имени).
Поведение: вызовы функции-перегрузки в SQL создают рёбра к «первой попавшейся» вершине —
это приемлемо для deploi validate (главное — все объекты в графе есть).
```

## 8. Риски и смягчения

| Риск | Смягчение |
|------|-----------|
| `codebase_hash` инвалидируется (имена .sql-файлов изменились) | Уже предусмотрен механизм `is_stale` — граф перестроится автоматически |
| Имя файла с SHA-суффиксом всё ещё >255 символов | Невозможно: макс. ≈ 86 символов (см. §4.2) |
| Старые `.dbm_graph/` несовместимы | `object_key` для неперегруженных объектов не меняется; для перегруженных граф просто перестроится (`is_stale`) |
| Edge detection не различает перегрузки | Зафиксировано как MVP-ограничение (Q3); разрешение вызовов → Phase 5+ |
| Регрессии в существующем deploi/test контракте | Деплой берёт путь из `object_source_file` (не из имени); контракт сохраняется |

## 9. Что НЕ входит в Phase 4

- Разрешение перегруженных вызовов в edge detection (type inference по аргументам) — Phase 5+.
- Нормализация алиасов типов (`varchar`↔`character varying`, `int4`↔`integer`) —
  не требуется, т.к. `argument_types` из `pg_type.typname` уже приходит нормализованным.
- SSH-key auth (Phase 3 follow-up), миграции с данными (Phase 5 в roadmap).
